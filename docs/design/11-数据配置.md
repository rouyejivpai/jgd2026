## 1. 目标产物

### 1.1 一句话

把「策划改数值」与「程序改代码」彻底解耦：所有数值、关卡、评价系数都在 `res://data/` 的 JSON 里，载入时**严格校验**，出错时报出**哪个文件、哪个字段**，而不是静默用默认值。

### 1.2 交付物清单

| 交付物 | 形式 | 说明 |
|---|---|---|
| `DataLoader` | `core/data/data_loader.gd` | 统一的 JSON 载入 + 校验 + 缓存 + 热重载 |
| `UnitTable` | `core/data/unit_table.gd` | 单位表查询与关卡级覆盖合成 |
| 单位表 | `res://data/units.json` | 见 3.1 |
| 评价系数 | `res://data/scoring.json` | 见 3.2（[08](08-评价与结算.md) 3.3） |
| 关卡清单 | `res://data/levels/manifest.json` | 见 3.3 |
| 机制说明 | `res://data/help/机制说明.md` | 由 [10](10-主界面与HUD.md) 读取 |
| 自动化用例 | `tools/smoke_test.gd` 增量 | 见 6.1 |

### 1.3 三条硬性要求

1. **脚本里不出现魔法数字**：伤害、射程、速度、系数一律从数据表取。
2. **载入失败必须显式报错**：给出文件路径 + 字段名 + 问题（不做静默降级、不用默认值兜底）——FR-UNIT-03。
3. **改数据不用重启引擎**：支持热重载（FR-UNIT-04、FR-SCORE-03）。

## 2. 系统边界

### 2.1 本系统负责

- 读取 `res://data/` 下的 JSON 与 Markdown。
- 字段存在性、类型、取值范围、枚举合法性的校验，并给出可定位的错误信息。
- 载入结果的内存缓存（避免每 tick 重复解析）。
- 热重载：重新读取指定数据表并替换缓存。
- **关卡级数值覆盖的合成**：把 `units.json` 的默认值与关卡 `overrides` 合成出单位实例的最终数值。
- 单位 id → 数值的查询接口。

### 2.2 本系统明确不负责

| 不负责 | 归属 |
|---|---|
| 数值的**平衡决策**（100 血、3 距离/秒是否合理） | 策划 |
| 关卡数据的**语义校验**（单位是否落在墙上、胜负条件参数是否合法） | [06 关卡数据与胜负条件](06-关卡数据与胜负条件.md) 的 `LevelData.validate()` |
| 运行时状态（血量、冷却、意图） | [04 单位与移动](04-单位与移动.md) |
| 存档与设置的读写 | `Save`（`autoload/save_manager.gd`，已就绪） |
| 关卡数据的**编辑** | [07 关卡编辑器](07-关卡编辑器.md) |
| 机制说明 Markdown 的**渲染** | [10 主界面与HUD](10-主界面与HUD.md)（本系统只提供文件路径） |

### 2.3 边界上的接口约定

- 本系统**只读**，从不写 `res://data/`（关卡的保存由 [07](07-关卡编辑器.md) 负责）。
- 本系统返回的是**不可变的值**（每次查询返回新构造的 `UnitStats` 或字典副本），避免调用方改到缓存。
- 校验分两层：**结构校验在本系统**（字段类型/范围），**语义校验在系统 06**（跨字段约束）。两者都失败时报错信息要能拼起来看。

## 3. 数据格式

### 3.1 `res://data/units.json`

**MVP 只录入教程三关实际用到的 4 种**（D-04）：`standard`、`standard_attack`、`ice`、`basic_enemy`。策划案中的 `ranged`（远射人工生命）与 `heavy_enemy`（强力高级敌人）**留到第一章再补**——避免出现「表里有但关卡里永远见不到、也无人验证」的条目。

> 这个决定顺带消掉了策划案的一处矛盾：原文中 `ranged` 与 `ice` 数值完全相同（仅 `ice` 多一条减速），疑为复制粘贴未改。MVP 只录入 `ice`，因此这个重复不再影响实现。

```json
{
  "version": 1,
  "units": {
    "standard": {
      "name": "标准-基础人工生命",
      "max_hp": 100, "move_speed": 3.0, "can_attack": false
    },
    "standard_attack": {
      "name": "标准-基础攻击人工生命",
      "max_hp": 100, "move_speed": 3.0, "can_attack": true,
      "range": 3, "damage": 10, "attack_interval": 1.0,
      "projectile_speed": 12.0, "projectile_radius": 0.3,
      "vision_radius": 0, "on_hit_status": ""
    },
    "ice": {
      "name": "冰寒人工生命",
      "max_hp": 30, "move_speed": 2.0, "can_attack": true,
      "range": 10, "damage": 50, "attack_interval": 2.0,
      "projectile_speed": 12.0, "projectile_radius": 0.3,
      "vision_radius": 0, "on_hit_status": "slowed"
    },
    "basic_enemy": {
      "name": "标准-基础1级敌人",
      "max_hp": 100, "move_speed": 3.0, "can_attack": true,
      "range": 5, "damage": 10, "attack_interval": 1.0,
      "projectile_speed": 12.0, "projectile_radius": 0.3,
      "vision_radius": 0, "on_hit_status": ""
    }
  }
}
```

字段规范（对应 [04](04-单位与移动.md) 3.1）：

| 字段 | 必填 | 类型 | 范围 | 默认 | 说明 |
|---|---|---|---|---|---|
| `name` | ✅ | string | 非空 | — | 显示名 |
| `max_hp` | ✅ | number | `> 0` | — | 生命值 |
| `move_speed` | ✅ | number | `>= 0` | — | 距离/秒 |
| `can_attack` | ✅ | bool | — | — | `false` 时下列攻击字段可省略 |
| `range` | 攻击单位必填 | number | `> 0` | — | 射程（距离） |
| `damage` | 攻击单位必填 | number | `>= 0` | — | 单发伤害 |
| `attack_interval` | 攻击单位必填 | number | `> 0` | — | 秒/发（= 1 / 攻速） |
| `projectile_speed` | ⬜ | number | `> 0` | `12.0` | 距离/秒 |
| `projectile_radius` | ⬜ | number | `> 0` | `0.3` | 命中盒半径（直径 0.6） |
| `vision_radius` | ⬜ | number | `>= 0` | `0` | `0` 表示取 `range` |
| `on_hit_status` | ⬜ | string | `""` / `"slowed"` | `""` | 命中附带状态 |

**数值来源说明**：以上数值全部取自策划案 3.5.1 / 3.5.2（[需求文档 7.1/7.2](../需求文档.md)）。

> ⚠️ **历史遗留提醒**：策划案原文中「远射人工生命」与「冰寒人工生命」的数值完全相同（仅后者多一条减速），疑为复制粘贴未改。MVP **只录入 `ice`**（D-04），因此这个重复不再影响实现。若第一章要启用远射人工生命，**先让策划区分两者数值**，不要自己顺手改。

**攻速换算**：策划案用「发/秒」，数据表用 `attack_interval`（秒/发）。`1 发/秒 → 1.0`；`0.5 发/秒 → 2.0`。这样战斗系统只需做减法（[05](05-战斗.md) 4.1），不需要除法。

### 3.2 `res://data/scoring.json`

```json
{ "version": 1, "complexity": 10.0, "beacon": 10.0, "time": 1.0 }
```

见 [08](08-评价与结算.md) 3.3。**已确认初值 C1=10、C2=10、C3=1**（D-14），即「1 条条件/行为」「1 个信标」都等价于 10 秒时间。

### 3.3 `res://data/levels/manifest.json`

```json
{ "version": 1, "levels": ["tutorial_01", "tutorial_02", "tutorial_03"] }
```

- **手写清单**（需求确认）：决定选关顺序，也决定「下一关」按钮的去向。
- 新增关卡：放一个 `tutorial_04.json`，再把 id 追加进 `levels` 数组（仍不需要改代码，满足 FR-LV-04）。
- 校验：数组内 id 不得重复；每个 id 必须有对应的 `levels/<id>.json`。

### 3.4 版本字段

所有 JSON 顶层带 `version`。载入时若 `version` 大于程序支持的版本 → 报错「数据文件版本过新」而不是尝试解析。这是后续加字段时**避免旧构建读到新格式而静默错乱**的保险。

## 4. 算法

### 4.1 载入流程

```
load_json(path) -> Dictionary:
    1. 文件不存在        → 报错「文件未找到: <path>」
    2. JSON 解析失败     → 报错「JSON 语法错误: <path>:<行>:<列>」（用 JSON.new().parse 的错误信息）
    3. 顶层是 Array 而非 Dictionary → 报错
    4. version 检查      → 过新则报错
    5. 交给各自的校验函数 → 逐字段校验，收集**全部**错误后一次性报出（不是遇到第一个就返回）
    6. 缓存并返回
```

**一次性报出全部错误**：策划改表时一次能看到所有问题，不用「改一个跑一次」。

### 4.2 校验（结构层）

```
validate_unit(id, dict) -> Array[String]:   # 返回错误列表
    - 必填字段缺失        → "units.json: units.<id>: 缺少必填字段 max_hp"
    - 类型不符            → "units.json: units.<id>.max_hp: 期望 number，实际 string"
    - 范围越界            → "units.json: units.<id>.max_hp: 必须 > 0，实际 0"
    - can_attack == true 时缺 range/damage/attack_interval → 逐条报出
    - on_hit_status 不在允许枚举 → 报出允许值
```

错误信息格式统一为：`<文件名>: <字段路径>: <问题>`。字段路径用点号表示层级，便于在编辑器里定位。

### 4.3 关卡级覆盖的合成

```
get_unit_stats(type_id, overrides) -> UnitStats:
    base = units[type_id]                    # 已校验
    merged = base.duplicate()
    for key in overrides:
        if not base.has(key):  报错「units.json 中 <type_id> 没有字段 <key>，无法覆盖」
        merged[key] = overrides[key]
    return UnitStats.from_dict(merged)
```

**覆盖只能覆盖已存在的字段**：防止关卡写错字段名后被静默忽略（那样会出现「我明明调了射程却没生效」的幽灵 bug）。

**覆盖不写回缓存**：`units.json` 的默认值永远不变（FR-UNIT-05：第二、三关敌人射程覆盖为 2，而表里仍是 5）。

### 4.4 热重载

```
reload_all() -> Array[String]:      # 返回错误列表
    清缓存 → 重新载入 units.json / scoring.json / manifest.json
    若某张表失败 → 保留该表的**旧缓存**并返回错误（不把游戏搞崩）
```

| 触发方式 | 说明 |
|---|---|
| 启动时 | 自动载入全部 |
| 编辑器内手动 | 提供 `reload_all()` 供调试与「改完立刻试」 |
| 文件监听 | **MVP 不做**（见 8.2）；要求「不重启引擎」用按钮触发即可满足 FR-UNIT-04 |

> FR-UNIT-04 的验收口径是「编辑器内改完直接试玩，不重启引擎」。按钮触发的 `reload_all()` 已满足；自动文件监听是体验优化，不阻塞。

### 4.5 缓存策略

| 数据 | 缓存形态 | 失效时机 |
|---|---|---|
| `units.json` | `Dictionary[String, Dictionary]`（原始校验过的字典） | `reload_all()` |
| `scoring.json` | `Dictionary` | `reload_all()` |
| `manifest.json` | `Array[String]` | `reload_all()` |
| 关卡 `levels/*.json` | **不缓存**（每次进入关卡重新读，量小） | — |

> 关卡不缓存是刻意的：编辑器保存后立刻试玩，必须读到新文件（[07](07-关卡编辑器.md) 4.3）。

## 6. 验收

### 6.1 冒烟测试用例

| 用例 | 断言 |
|---|---|
| 正常载入 | `units.json` / `scoring.json` / `manifest.json` 全部载入无错 |
| 文件缺失 | 指向不存在的路径 → 错误信息含路径，不崩溃 |
| JSON 语法错 | 故意写成 `{"a":}` → 报错含行号/列号 |
| 缺必填字段 | 删掉 `max_hp` → 报错含 `units.<id>.max_hp` |
| 类型错 | `max_hp: "100"` → 报错说期望 number |
| 范围错 | `max_hp: 0` → 报错说必须 > 0 |
| 攻击单位缺射程 | `can_attack: true` 但无 `range` → 报错 |
| 枚举错 | `on_hit_status: "burn"` → 报错并列出允许值 |
| 一次报出全部错误 | 同时构造 3 个错误 → 错误列表长度为 3 |
| 版本过新 | `version: 99` → 报错 |
| 覆盖生效 | `basic_enemy` + `{"range": 2}` → `effective_range == 2`，而表里仍是 5（FR-UNIT-05） |
| 覆盖未知字段 | `{"rnage": 2}` → 报错「字段不存在」 |
| 覆盖不污染缓存 | 覆盖后再次 `get_unit_stats("basic_enemy")`（无覆盖）→ `range` 仍是 5 |
| 热重载 | 改 `scoring.json` 后 `reload_all()` → 新系数生效，无需重启（FR-SCORE-03 / FR-UNIT-04） |
| 单表失败保留旧值 | 把 `scoring.json` 写坏 → `reload_all()` 返回错误，但旧系数仍可用、游戏不崩 |
| manifest 校验 | 含重复 id 或指向不存在的关卡文件 → 报错 |
| 关卡不缓存 | 连续两次 `load_level(id)` 读到的是文件当前内容（改文件后第二次能读到新值） |

### 6.2 对应需求验收

| 需求编号 | 覆盖方式 |
|---|---|
| FR-UNIT-01 | 数值全部来自 JSON（脚本中无数字）：用例「覆盖生效」+ 代码审查 |
| FR-UNIT-02 | 字段覆盖齐全（3.1 表与 [04](04-单位与移动.md) 3.1 一致） |
| FR-UNIT-03 | 缺字段/类型错/范围错均报错且指明位置 |
| FR-UNIT-04 | 热重载 |
| FR-UNIT-05 / FR-TEST-06 | 关卡级覆盖生效且不污染全局表 |
| FR-SCORE-02 / 03 | 系数来自 `scoring.json` + 热调 |
| FR-LV-02 | `manifest.json` 提供关卡列表与顺序 |
| FR-UNIT-01（反例） / FR-TEST-04 | 改 `units.json` 的 `damage` 后重启 → 战斗结果随之变化 |

## 7. 风险与开放项

| 风险 | 说明 | 缓解 |
|---|---|---|
| 策划改表时的字段名拼写 | 拼错字段名在多数实现里会静默忽略 | 覆盖时校验字段存在性（4.3）；必填字段缺失直接报错 |
| 「一次报出全部错误」的实现复杂度 | 需要收集而非抛出 | 校验函数统一返回 `Array[String]`，不抛异常 |
| `attack_interval` 与「发/秒」换算 | 数据表与策划案用不同单位，易搞混 | 3.1 明确写换算关系；策划案数值在注释里标注对应的「发/秒」 |
| 关卡不缓存带来的重复 IO | 每次进关都读文件 | 关卡文件 < 几 KB，代价可忽略；换来「改完立刻试」的确定性 |
| `version` 字段的维护 | 加字段时忘记升版本 | 约定：**删除或改语义**时必须升 `version`；仅新增可选字段不必升 |
| 热重载与运行中状态 | 载入新数值时场上已有单位仍用旧值（`UnitStats` 已构造） | 预期行为：热重载只影响之后创建的单位；重置关卡后全部生效 |

**开放项（MVP 不做，已确认）**：

1. **文件自动监听**（改文件即时生效）——需要 `FileSystemWatcher` 或轮询，收益有限，用按钮触发即可。
2. **本地化/多语言**——所有显示名目前硬编码中文在 `units.json` 的 `name` 里；若要多语言，改为 `name_key` 并加语言表。
3. **数据表版本迁移**——只有一个 `version: 1`，不做迁移逻辑；格式变化时手工改数据。
