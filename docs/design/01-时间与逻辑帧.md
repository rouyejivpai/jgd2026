## 1. 目标产物

### 1.1 一句话

提供**与倍速无关的固定步长逻辑 tick**：无论 1x/2x/3x，每次 tick 推进的游戏时间恒为 `1/60` 秒，从而保证同一关在任意倍速下胜负与评价完全一致（FR-TEST-03）。

### 1.2 交付物清单

| 交付物 | 形式 | 说明 |
|---|---|---|
| `GameClock` | `src/core/time/game_clock.gd` | 累加器、`tick` 信号、倍速设置、tick 计数 |
| 关卡级执行顺序编排 | 见 4.3；落在 `src/core/level/level_session.gd` | **`GameClock` 自身不做编排**，只发信号 |
| 自动化用例 | `tools/smoke_test.gd` 增量 | 见 6.1，全部可在无头模式下断言 |

### 1.3 三条硬性契约

1. **tick 步长恒为 `1/60` 秒游戏时间**，不受倍速、帧率、暂停影响。
2. **一次 tick 内所有逻辑读到的都是同一个固定步长**；任何系统不得自行用 `delta` 做数值积分。
3. 倍速只改变「每个渲染帧累加多少游戏时间」，从而改变**每秒产生多少个 tick**，不改变 tick 的内容。

## 2. 系统边界

### 2.1 本系统负责

- 游戏时间累加与 tick 触发。
- 倍速（1x/2x/3x）换算。
- tick 序号计数（从 0 开始，供调试、评价计时与确定性对比）。
- 单帧 tick 数量上限保护，防止卡顿时的「死亡螺旋」。
- 重置（重置关卡时归零）。

### 2.2 本系统明确不负责

| 不负责 | 归属 |
|---|---|
| 各系统在 tick 内的执行顺序 | `LevelSession`（见 4.3），本系统只发信号 |
| 暂停、顿帧、慢动作 | `autoload/game_state.gd`（`Game`，已就绪） |
| 编制期/推演期/结算期的判定 | [06 关卡数据与胜负条件](06-关卡数据与胜负条件.md) |
| 任何玩法逻辑 | 02–05、08 |
| 计时器的显示 | [10 主界面与HUD](10-主界面与HUD.md) |

### 2.3 特别注意：不要用 `Engine.time_scale` 做倍速

**决策**：倍速用**我们自己的乘数**，不用 `Engine.time_scale`。

| 理由 | 说明 |
|---|---|
| 现有 `Game.hitstop()` 已占用 `Engine.time_scale`（顿帧时置 0） | 若倍速也写这个值，两者会互相踩，且顿帧会把倍速设置丢掉 |
| `Engine.time_scale` 会缩放 `delta` | 用固定步长累加器时，缩放容易产生「累加器突然满足多次 tick」的抖动 |
| 可预测性 | 自持乘数让「1x/2x/3x」的行为在代码里一眼可读 |

**附带影响**：现有 `Game.hitstop()` / `Game.slowmo()` 依赖 `Engine.time_scale`。引入本系统后，顿帧**同时**冻结我们的累加器（因为 `time_scale = 0` 时 `_physics_process` 的 `delta` 为 0），这恰好是想要的效果，不需要额外改动。若后续需要「不受倍速影响的打击感」，再单独讨论（见第 8 章）。

**已确认的顿帧口径（D-19）**：顿帧的**真实时长恒定**，不随倍速缩放——3x 下打击感不减弱。当前实现天然满足这一点：`Engine.time_scale = 0` 冻结的是**游戏时间**，而 `Game.hitstop()` 内部的等待用的是真实时间（`create_timer(..., ignore_time_scale = true)`），因此倍速为 3x 时顿帧的真实秒数不变。**不要在顿帧里乘 `speed_multiplier`**。

## 3. 数据结构与接口

### 3.1 常量

| 常量 | 值 | 说明 |
|---|---|---|
| `TICK_RATE` | `60` | 逻辑帧率 |
| `TICK_DELTA` | `1.0 / 60.0` | 每个 tick 推进的游戏秒数 |
| `MAX_TICKS_PER_FRAME` | `16` | 单帧 tick 上限（正常 1x 下为 1，3x 下为 3） |
| `SPEED_CHOICES` | `[1.0, 2.0, 3.0]` | 可选倍速（FR-FLOW-03） |

### 3.2 对外接口

| 成员 | 类型 | 说明 |
|---|---|---|
| `signal tick` | `signal` | **无参数**；订阅者自行按需读取 `clock.tick_index` |
| `tick_index` | `int` | 已执行的 tick 数，从 0 开始 |
| `speed_multiplier` | `float` | 当前倍速，默认 1.0 |
| `set_speed_multiplier(value)` | 方法 | 见 4.2（含防抖处理） |
| `reset()` | 方法 | 累加器与 `tick_index` 归零 |
| `game_time` | `float` | `tick_index * TICK_DELTA`，评价计时用（同时由系统 06 独立统计，见 6.4） |

### 3.3 与现有内核的关系

- 本系统是 `Node`，**不做 autoload**：挂载在玩法场景下即可，编辑器场景不需要它。
- 暂停走 Godot 原生 `get_tree().paused`：暂停时 `_physics_process` 不执行，累加器自然停止（无需自行判断）。
- 编制期由 `LevelSession` 决定「要不要把 `tick` 信号接到逻辑上」；更简单的做法是 `LevelSession` 在编制期直接**不订阅**——两种做法都可行，推荐后者（本系统无需知道编制期的存在）。

## 4. 算法

### 4.1 累加与触发

```gdscript
func _physics_process(delta: float) -> void:
    if speed_multiplier <= 0.0:
        return
    _accumulator += delta * speed_multiplier        # 倍速只作用于累加速率
    var budget := MAX_TICKS_PER_FRAME
    while _accumulator >= TICK_DELTA and budget > 0:
        _accumulator -= TICK_DELTA                  # 固定步长，不随倍速改变
        tick_index += 1
        budget -= 1
        tick.emit()
    if budget == 0 and _accumulator >= TICK_DELTA:
        _accumulator = 0.0                          # 丢弃积压，防死亡螺旋
        push_warning("GameClock: 单帧 tick 数超上限，已丢弃积压时间")
```

**要点**

- `TICK_DELTA` 是常量，`delta * speed_multiplier` 只影响**多久攒够一个 tick**。
- 3x 时每帧攒 `3 * delta`，因此每秒 tick 数约为 1x 的 3 倍 —— 这正是 FR-FLOW-03 期望的「耗时约 1/3」。
- 低帧率保护：若渲染掉到 30fps，1x 下每帧攒 `1/30` 秒 = 2 个 tick，仍在预算内；3x 下每帧攒 `1/10` 秒 = 6 个 tick，也在预算内。预算 16 对应约 11fps 的极端情况，超出即丢弃积压。

### 4.2 倍速切换的防抖

```
set_speed_multiplier(v):
    先把累加器清 0，再设置新倍速
```

**为什么必须先清累加器**：若切换瞬间累加器里已攒了 `0.9 * TICK_DELTA`，切到 3x 后下一帧会立刻攒够并在同一帧内连发多个 tick，表现为「切倍速时画面猛跳一下」。清零后切换点始终对齐到 tick 边界。

**验收**：`set_speed_multiplier` 调用前后，`tick_index` 不跳变超过 1。

### 4.3 一个 tick 内的执行顺序（由 `LevelSession` 编排）

`GameClock` 只发 `tick` 信号；顺序由关卡会话按固定次序同步调用，**不使用多个订阅者的隐式顺序**（Godot 的信号回调顺序不可靠，不能作为逻辑顺序的依据）。

```
tick 触发
  1. signal_store.commit()              提交上一 tick 暂存的信号(D4)
  2. rule_engine.evaluate_all()         逐单位求值，产出 Intent
  3. unit.apply_intents()               应用意图 + 延迟计时器递减
  4. movement.step()                    直线移动、撞墙停止
  5. combat.step()                      冷却、生成子弹
  6. projectile.step()                  子弹推进、命中、伤害
  7. battle_state.cleanup_dead()        清理死亡单位
  8. win_condition.evaluate()           胜负检查
  9. statistics.sample()                统计采样（条件数/行为数/信标数/耗时）
```

> 顺序**必须**在 `LevelSession` 中用显式调用表达，而不是让 9 个系统各自 `connect(tick)`。后者在重构时极易因订阅顺序变化而静默改变玩法结果。

### 4.4 重置

`reset()` 把 `_accumulator`、`tick_index` 归零。重置关卡时由 `LevelSession` 调用（FR-FLOW-04）。**注意**：重置要保留玩家已写的指令与信标，那些数据不在本系统内，本系统只清时间。

## 6. 验收

### 6.1 冒烟测试用例

| 用例 | 构造 | 断言 |
|---|---|---|
| 步长恒定 | 手动推进 60 个渲染帧（每帧 `delta = 1/60`），倍速 1x | `tick_index == 60`，`game_time ≈ 1.0` |
| 倍速不改变 tick 内容 | 同一套 3 条指令，分别在 1x 与 3x 下跑到同一 `tick_index` | 两次的单位坐标、血量、信号表**完全相等**（FR-TEST-03 的核心） |
| 3x 耗时约为 1/3 | 记录跑到 `tick_index == 600` 所需的渲染帧数 | 3x 的帧数约为 1x 的 1/3（容差 ±2 帧） |
| 切换倍速不跳变 | 中途调用 `set_speed_multiplier` | `tick_index` 单帧增量 ≤ 1，且累加器被清零 |
| 单帧上限 | 传入一个极大的 `delta`（模拟卡顿） | 单帧最多触发 `MAX_TICKS_PER_FRAME` 个 tick，并产生一条警告 |
| 暂停停止推进 | 设 `get_tree().paused = true` 后推进若干帧 | `tick_index` 不变 |
| 重置归零 | 推进 100 个 tick 后 `reset()` | `tick_index == 0`，累加器为 0 |

### 6.2 无头运行说明

上述用例都不需要渲染：`GameClock` 是纯逻辑 `Node`，在 `smoke_test` 中可以手动调用 `_physics_process(1.0/60.0)` 精确控制推进，**不要**依赖真实帧率。这是 FR-TEST-03 能被自动化的前提。

**两条实测得到的硬性要求**（M0 期间踩到，已写进用例）：

1. **测试里必须先 `clock.set_physics_process(false)`。**
   `GameClock` 自己就是靠 `_physics_process` 驱动的；手动喂 `delta` 时若不同时关掉引擎的自动调用，
   两者会**叠加**，tick 数就取决于跑测试时的帧率——正好是本系统要消灭的那种不确定性。
2. **跨文件引用本类时用 `preload`，不要用 `class_name`。**
   本工程的沙箱禁止子进程写 `res://.godot/`，`global_script_class_cache.cfg` 无法更新，
   新脚本的 `class_name` 不会进入全局类缓存。约定见 [`tools/smoke_test.gd`](../../tools/smoke_test.gd) 顶部注释。
   另外：preload 得到的常量**不能当类型标注**（`var clock: GameClockScript` 会直接编译失败），
   只能标引擎内置类型，如 `var clock: Node = ClockScript.new()`。

**倍速的语义再强调一次**（写用例时最容易写错的地方）：

> 倍速是「同样的**真实时间**推进 N 倍的**游戏时间**」，而不是「每帧只跑一个 tick」。
> 在物理帧率固定 60Hz 的前提下，**3x 时每个物理帧就会产生 3 个 tick**。
> 所以「3 帧产生 3 个 tick」是错的，正确是 9 个；而「600 个 tick 只用 200 帧跑完」才是倍速该有的表现。

### 6.3 对应需求验收

| 需求编号 | 覆盖方式 |
|---|---|
| FR-FLOW-01 | 编制期不订阅 `tick`（由系统 06 断言单位坐标不变） |
| FR-FLOW-02 | 点开始后开始订阅，`tick_index` 从 0 递增 |
| FR-FLOW-03 | 3x 耗时约为 1/3 |
| FR-FLOW-06 / FR-TEST-03 | 倍速不改变 tick 内容（最关键的一条） |

### 6.4 评价计时的口径

「所用时间」由本系统提供 `game_time`（= `tick_index * TICK_DELTA`），但**统计归属系统 08**：

- 用 `game_time` 意味着「按游戏内时间计」，同一关无论玩家用几倍速，用时数值相同——与 FR-FLOW-06「倍速不得影响结算结果」一致。
- 需求 12.4-④ 尚未确定「所用时间是游戏内时间还是真实耗时」；本设计**默认游戏内时间**。若改为真实耗时，则系统 08 改用 `Time.get_ticks_msec()` 自行统计，本系统无需改动。

## 7. 风险与开放项

| 风险 | 说明 | 缓解 |
|---|---|---|
| 物理帧率被改动 | 若有人把 `physics/common/physics_ticks_per_second` 从 60 改掉，累加次数会变（tick 数不变，因为按时间累加），但每帧 tick 数分布会变 | tick 语义只依赖**游戏时间**，不依赖物理帧率；用例 6.1 用固定 `delta` 断言即可不受影响 |
| 顿帧与倍速共存 | 顿帧走 `Engine.time_scale = 0`，此时 `delta = 0`，累加器自然冻结 | 已确认行为正确（D-19：顿帧真实时长恒定）；但 `Game.hitstop()` 结束后会强制 `time_scale = 1.0`，若将来倍速也改用它就会冲突——**保持现状（倍速不用 time_scale）即可** |
| 累积误差 | `float` 累加会漂移 | 用例以 `tick_index` 为准做断言，不用累加器值做判据；`game_time` 由 `tick_index` 推导而非累加 |
| 丢弃积压导致时长偏差 | 极端卡顿时会丢时间，使评价计时与真实耗时不符 | 仅在大卡顿时发生；3x 下预算仍有充足余量 |

**开放项**：~~是否需要「不随倍速缩放的打击感」（即顿帧的真实时长不因 3x 而缩短）~~ → **已确认：不随倍速缩放（D-19）**，当前实现天然满足（见 2.3）。
