## 1. 目标产物

### 1.1 一句话

把「玩家写的规则表」在**每个逻辑 tick** 翻译成一组**本 tick 生效的意图**（移动 / 开火 / 信号 / 阻塞），并对冲突与持续状态给出确定结果。

### 1.2 交付物清单

| 交付物 | 形式 | 说明 |
|---|---|---|
| `Rule` 运行时类 | `rule.gd` | 一条指令：`enabled` + `conditions` + `condition_logic` + `actions` |
| 条件类型与求值 | `condition.gd` + 子类 | 5 种条件（见 3.2），纯函数式求值，无副作用 |
| 行为类型与落地 | `action.gd` + 子类 | 5 种行为（见 3.3），只产出意图，不直接改世界 |
| 枚举与冲突键表 | `enums.gd` | 条件/行为枚举、`冲突键`映射、UI 显示名 |
| 求值主流程 | `rule_engine.gd` | 逐条求值 → 冲突覆盖 → 输出 `Intent` |
| `Intent` 结构 | 见 4.1 | 本 tick 的意图集合，交给系统 04/05 执行 |
| 自动化用例 | `tools/smoke_test.gd` 增量 | 覆盖 7.2 全部验收项，**不依赖渲染** |

### 1.3 必须成立的语义（全部已在需求文档确认）

1. 每 tick 从第 1 条指令向下逐条求值，收集**所有**条件成立的指令（[需求 5.4](../需求文档.md)）。
2. 同类行为按冲突键分组，**顺序最靠后**的生效（后覆盖前）。
3. 不同冲突键的行为**同时生效**。
4. 条件转假**不清空**持续型意图（`move` / `fire_mode` 保持）。
5. **延迟是阻塞型计时器**，不参与冲突键覆盖；阻塞期间单位不动也不开火。
6. 本 tick 写入的信号**下一 tick** 才被条件读到。
7. 引用已被撤回信标的指令**整条跳过**，并在 UI 标黄。
8. 指令数组下标即优先级，行号为 `1..n` 动态刷新。

## 2. 系统边界

### 2.1 本系统负责

- 条件的真值求值（视野、信号、与信标距离、血量、敌人状态）。
- 冲突键计算与「后覆盖前」仲裁。
- 持续型意图的保持（`move` / `fire_mode`）。
- 延迟计时器的递减与阻塞标志。
- 信号写入的**暂存**与下一 tick 提交（时序由本系统规定，实际存储在系统 03 的全局信号表）。
- 指令合法性检查（引用不存在的信标/信号 → 整条跳过，并标记 `invalid_reason` 供 UI 标黄）。
- 输出本 tick 的 `Intent`。

### 2.2 本系统明确不负责

| 不负责 | 归属 |
|---|---|
| 单位的实际位移、撞墙停止 | [04 单位与移动](04-单位与移动.md) |
| 子弹生成、飞行、命中、伤害 | [05 战斗](05-战斗.md) |
| 「最近敌人」的查询实现 | [03 网格地图](03-网格地图.md) 的实体注册表 |
| 单位的血量、减速层数**存储** | [04 单位与移动](04-单位与移动.md)（本系统只读取求值） |
| 指令的编辑 UI、拖拽排序交互 | [09 指令编辑界面](09-指令编辑界面.md) |
| 延迟计时器的**视觉**表现 | [10 主界面与HUD](10-主界面与HUD.md) |
| 信号与信标的**渲染** | [10 主界面与HUD](10-主界面与HUD.md) |
| tick 何时到来 | [01 时间与逻辑帧](01-时间与逻辑帧.md) |

### 2.3 边界上的接口约定

- 本系统**只读**单位状态（血量、状态、坐标）与全局信号表，**不写**（信号写入走暂存区，见 4.3）。
- 本系统**不持有**单位引用做修改，只产出 `Intent`；由系统 04 取走并应用。
- 「装置互动」行为在 MVP 中**只保留枚举与数据结构，UI 不出现、求值直接跳过**（[需求 12.5a](../需求文档.md)）。

## 3. 数据结构

### 3.1 指令（Rule）

| 字段 | 类型 | 说明 |
|---|---|---|
| `enabled` | `bool` | 禁用后完全不参与求值，位置保留（FR-CMD-09） |
| `condition_logic` | `Logic` 枚举 | `AND` / `OR`，一条指令只用一种，不做嵌套 |
| `conditions` | `Array[Condition]` | 0..n；0 个条件即**无条件成立** |
| `actions` | `Array[Action]` | 1..n；同类型行为只允许一个（UI 层约束，引擎层兼容） |
| `invalid_reason` | `String` | 运行时计算：引用不存在的信标/信号时填写，供 UI 标黄 |

**数组下标即优先级**：执行顺序 = 数组顺序，行号 `1..n` 由 UI 动态刷新。

### 3.2 条件类型（5 种）

| 枚举 | 参数 | 求值依据 |
|---|---|---|
| `ENEMY_IN_VISION` | `radius: float`（`<=0` 表示取单位当前攻击射程） | 场上有敌方单位与本单位距离 `<= radius`（欧氏距离，墙不遮挡） |
| `SIGNAL_STATE` | `signal_index: int`、`want: bool` | 读**本 tick 生效的**信号表（D4 时序） |
| `BEACON_DISTANCE` | `beacon_index: int`、`op: Compare`、`value: float` | 本单位到该信标中心的距离与 `value` 比较 |
| `SELF_HP` | `op: Compare`、`percent: float` | 本单位当前血量百分比与 `percent` 比较 |
| `ENEMY_HAS_STATUS` | `status: Status`、`want: bool` | 视野内**任一**敌人持有/不持有该状态即为真 |

`Compare` 枚举：`LT` / `LE` / `EQ` / `GE` / `GT`。
`Status` 枚举（MVP 只有）：`SLOWED`（减速）。

> `ENEMY_HAS_STATUS` 用「任一敌人」而不是「最近敌人」，是为了避免引入 D3 禁止的「单位记忆目标」状态。

### 3.3 行为类型（5 种）

| 枚举 | 参数 | 冲突键 | 类型 |
|---|---|---|---|
| `SET_FIRE_MODE` | `fire: bool` | `fire_mode` | 持续型 |
| `MOVE_ALONG_BEACONS` | `beacon_indices: Array[int]`（有序） | `move` | 持续型 |
| `SET_SIGNAL` | `signal_index: int`、`value: bool` | `signal:<n>` | 瞬时型（写暂存区） |
| `DELAY` | `seconds: float` | **无**（阻塞型，见 3.4） | 阻塞型 |
| `INTERACT_DEVICE` | `device_id: int`、`kind` | `interact:<id>` | **MVP 不实现** |

### 3.4 延迟的阻塞语义

- `DELAY` 不产生冲突键，因此**不会被其它指令覆盖，也不覆盖别人**。
- 生效时设置单位的 `delay_remaining = max(delay_remaining, seconds)`（见 4.4 的第 3 条决策）。
- `delay_remaining > 0` 期间：单位**不移动、不开火**（系统 04 应用意图时跳过），但**其它行为照常**（信号照写）。
- 结束后自动解除，恢复执行当时仍然成立的移动与开火意图（意图本身未被清空）。

## 4. 求值算法

### 4.1 输出结构 Intent

| 字段 | 说明 |
|---|---|
| `move_intent` | `null` 或「目标信标序列 + 当前序号」 |
| `fire_intent` | `null` 或 `bool`（开火/停火） |
| `signal_writes` | 本 tick 要写入暂存区的 `(index, value)` 列表 |
| `delay_request` | `null` 或 `float`（请求的阻塞秒数） |
| `matched_rule_indices` | 本 tick 命中的指令下标（调试与 UI 高亮用） |

### 4.2 主流程（每 tick 一次，按单位遍历）

单位遍历顺序：**按实体 id 升序**（保证确定性，见 FR-TEST-08）。

```
1. 若 unit.delay_remaining > 0：本 tick 输出「空意图 + 保持既有意图」，不评估任何条件
   （延迟期间规则不刷新，避免计时结束时意图被中途改写）

2. 收集命中指令：按数组顺序遍历
   - enabled == false            → 跳过
   - 引用不存在的信标/信号       → 跳过，写 invalid_reason
   - 求值条件（AND 全真 / OR 任一真；0 个条件视为真）
   - 命中则用冲突键记账：table[conflict_key] = action（后写覆盖先写）

3. 从 table 取出最终生效行为，生成 Intent

4. 应用持续型意图的保持与重置规则（见 4.3）

5. 返回 Intent
```

### 4.3 持续型意图的保持与重置

| 情形 | 处理 |
|---|---|
| 本 tick 有 `move` 行为生效 | 若其信标序列与单位当前序列**值相等** → **保持当前序号**；否则 → 换成新序列并把序号重置为 0 |
| 本 tick **没有** `move` 行为生效 | **保持**既有移动意图与序号不变（FR-CMD-07） |
| 本 tick 有 `fire_mode` 生效 | 覆盖为新的开火/停火值 |
| 本 tick **没有** `fire_mode` 生效 | **保持**既有开火意图不变 |

> **为什么「值相等则保持序号」是必须的**：玩家的常见写法是「条件成立时沿着 1→2→3 移动」。若每 tick 刷新都从信标 1 重新开始，单位会在 1 和 2 之间**来回震荡**。按值比较可避免这个陷阱，且不需要玩家理解任何内部状态。

### 4.4 关键实现决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | 条件求值是**纯函数**，不得修改任何状态 | 可单测、可重复调用（幂等性要求） |
| 2 | 冲突键用 `String` 做表键，`signal:<n>`、`interact:<id>` 动态拼接 | 一张表覆盖全部行为类型 |
| 3 | 延迟计时器取 `max(现值, 新值)`，**不叠加** | 多条延迟同时命中时行为可预测；「停止 1 秒 + 停止 2 秒」应为 2 秒而非 3 秒 |
| 4 | 信号写入**暂存区**，tick 末由系统 01 统一提交 | 满足「下一 tick 生效」 |
| 5 | 无效指令**整条跳过**，不做部分执行 | 需求 12.1 决策；可预测、好测试 |
| 6 | 本系统不缓存任何跨 tick 状态，**除了**单位自身持有的移动序号与延迟计时器 | 状态集中在单位上，便于重置与序列化 |

## 6. 时序细节

### 6.1 一个 tick 内的位置

```
tick 开始
  ├─ 信号提交（把上一 tick 暂存的写入正式生效）      ← 系统 01 执行
  ├─ 【本系统】对每个单位按 id 升序求值 → Intent
  ├─ 系统 04 应用意图 + 移动
  ├─ 系统 05 开火 + 子弹 + 命中 + 死亡清理
  └─ 系统 06 胜负检查
tick 结束
```

### 6.2 延迟按 tick 递减

延迟剩余量在每个 tick 的「应用意图」阶段减去一个 `tick_delta`（`1/60`）。因此：

- 「停止 1 秒」= 60 个 tick。
- 倍速不影响秒数语义，只影响真实耗时（3x 时真实耗时约 1/3）——符合 FR-FLOW-03 的验收口径。

### 6.3 延迟期间是否重新求值

**不重新求值**（见 4.2 第 1 步）。理由：若延迟期间继续求值，计时结束那一刻生效的可能是延迟期间被刷新的意图，玩家难以预期；跳过求值让「停止 N 秒」成为一个干净的时间窗。

## 7. 验收

### 7.1 冒烟测试用例（不依赖渲染）

| 用例 | 构造 | 断言 |
|---|---|---|
| 覆盖语义 | 规则 1「无条件→停火」、规则 2「视野有敌→开火」，场上有敌 | 最终 `fire_intent == true`（需求 5.4 原文示例） |
| 持续意图保持 | 规则 1「无条件→移动 1→2」，规则 2「视野有敌→开火」 | 敌人离开视野后 `move_intent` 与序号不变，不抖动 |
| 序号不重置 | 条件持续成立、每 tick 刷新同一序列 `1→2→3` | 单位沿 1→2→3 前进，不在 1/2 之间震荡 |
| 序列变化则重置 | 先 `1→2→3` 走到 2，再刷新为 `3→4` | 序号重置为 0，目标变为信标 3 |
| 信号次 tick 生效 | 规则 A 写信号 1 开；规则 B 以「信号 1 开」为条件 | 第 1 tick B 不命中，第 2 tick 起命中 |
| 延迟阻塞 | 「无条件→延迟 1 秒」+「无条件→移动」 | 60 个 tick 内不移动，之后恢复移动；期间不清空移动意图 |
| 延迟不叠加 | 同时命中两条延迟（1 秒、2 秒） | 阻塞 2 秒而非 3 秒 |
| 无效指令跳过 | 移动行为引用已被撤回的信标 | 整条跳过且 `invalid_reason` 非空，其余指令照常生效 |
| 与/或逻辑 | 两个条件的真值表 | `AND` 与 `OR` 各自符合预期 |
| 禁用指令 | 一条命中的指令设 `enabled = false` | 不参与求值，其它指令结果不变 |
| 实体顺序确定性 | 两个单位规则互不依赖，重复跑 100 次 | `matched_rule_indices` 每次完全一致 |

### 7.2 对应需求验收

| 需求编号 | 由哪个用例覆盖 |
|---|---|
| FR-CMD-01 / FR-TEST-01 | 覆盖语义 |
| FR-CMD-02 | 视野条件（系统 03 提供半径查询） |
| FR-CMD-03 | `actions` 同类型唯一（UI 约束 + 引擎容错） |
| FR-CMD-04 | 与/或逻辑 |
| FR-CMD-05 | 覆盖语义 + 三条同类行为 |
| FR-CMD-06 | 不相冲突行为同时生效（信号 + 移动同 tick） |
| FR-CMD-07 / FR-TEST-02 | 持续意图保持 |
| FR-CMD-08 / FR-CMD-09 | 序号不重置 / 禁用指令 |
| 需求 5.4 延迟条款 | 延迟阻塞 / 延迟不叠加 |
| 需求 D4（12.1） | 信号次 tick 生效 |
| 需求 12.1（无效指令） | 无效指令跳过 |
| FR-TEST-08 | 实体顺序确定性 |

## 8. 风险与开放项

| 风险 | 说明 | 缓解 |
|---|---|---|
| **语义返工** | 这是全项目最容易返工的地方（见概设 M1 提示） | M1 阶段先把本系统最小版本 + 7.1 全部用例做出来，再动其它系统 |
| 震荡类陷阱 | 「条件持续成立 + 移动序列刷新」是玩家极可能踩的坑 | 已在 4.3 用「值相等则保持序号」消除；UI 上不需要暴露 |
| `ENEMY_IN_VISION` 半径语义 | `radius <= 0` 表示取当前射程，而射程可被关卡覆盖 | 求值统一走 `unit.effective_range`，不要直接读全局表 |
| 延迟与倍速 | 延迟按 tick 递减，秒数语义与倍速解耦 | 已在 6.2 明确；验收用 tick 计数断言而非真实时间 |
| 「装置互动」占位 | MVP 不实现，但枚举要先留好 | `INTERACT_DEVICE` 求值恒为「跳过」，UI 不渲染该选项 |

**待确认**（不阻塞开工，M2 结束前需给答复）：`ENEMY_HAS_STATUS` 是否应该改为「最近敌人持有该状态」——当前按「任一敌人」实现，若策划希望「只对正在减速的那个敌人才开火」则需改为最近敌人语义。
