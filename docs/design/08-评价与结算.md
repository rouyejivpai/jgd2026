## 1. 目标产物

### 1.1 一句话

把「这局玩得怎么样」量化成**一个越低越好的分数**，并统计出三个分项（指令复杂度 / 信标成本 / 时间成本），让玩家能够通过「少写指令、少放信标、更快通关」来刷分。

### 1.2 交付物清单

| 交付物 | 形式 | 说明 |
|---|---|---|
| `Statistics` | `result/statistics.gd` | 每局统计量的采集与累加 |
| `Scoring` | `result/scoring.gd` | 三项分项与最终得分的计算 |
| 系数配置 | `res://data/scoring.json` | C1 / C2 / C3，可热调（FR-SCORE-02/03） |
| 最佳记录读写 | 走 `Save`（`autoload/save_manager.gd`） | 每关一个最低分（FR-SCORE-04） |
| 自动化用例 | `tools/smoke_test.gd` 增量 | 见 6.1 |

### 1.3 公式（需求 10.1）

```
指令复杂度 = (行为数量 + 条件数量) × C1
信标成本   = 信标数量 × C2
时间成本   = 所用时间 × C3
最终得分   = 指令复杂度 + 信标成本 + 时间成本      # 越低越好
```

## 2. 系统边界

### 2.1 本系统负责

- 采集并累加每局统计量：条件数、行为数、信标数、用时。
- 按公式与系数计算三个分项与最终得分。
- 读 `scoring.json`；支持运行时重新载入（热调）。
- 与 `Save` 协作读写每关最佳（最低）得分，并判定是否刷新记录。
- 产出结算数据对象（含分项明细），供系统 10 渲染。

### 2.2 本系统明确不负责

| 不负责 | 归属 |
|---|---|
| 判定胜负 | [06 关卡数据与胜负条件](06-关卡数据与胜负条件.md) |
| 「用时」的计时实现 | [01 时间与逻辑帧](01-时间与逻辑帧.md)（提供 `game_time`） |
| 统计量的**来源数据**（规则表、信标列表） | 系统 02 / 信标层 |
| 结算界面的排版与按钮 | [10 主界面与HUD](10-主界面与HUD.md) |
| 系数的**取值决策**（配平） | 策划（需求 12.4-④） |
| 存档的底层读写 | `Save`（已就绪） |

### 2.3 边界上的接口约定

- 本系统**不读场景树**；统计量由 `LevelSession` 在每 tick 第 9 步调用 `statistics.sample(session)` 采集，或由会话在结算时一次性快照传入。
- 失败时不计算得分（FR-SCORE-06）：本系统只在 `verdict == WIN` 时被调用。

## 3. 数据结构

### 3.1 统计量（`Statistics`）

| 字段 | 类型 | 采集时机 | 口径 |
|---|---|---|---|
| `condition_count` | `int` | 结算时快照 | **全部 `enabled == true` 的指令**中累计的条件个数（含被覆盖而未生效的指令） |
| `action_count` | `int` | 结算时快照 | 同上，累计的行为个数 |
| `beacon_count` | `int` | 结算时快照 | **本局实际放置**的信标数（重置后重新放置则按最新一次计） |
| `elapsed_time` | `float` | 每 tick 累计 | 从点开始到结算的**游戏内时间**（`clock.game_time`） |

### 3.2 结算数据对象（`ResultData`）

| 字段 | 说明 |
|---|---|
| `level_id` | 关卡 id |
| `verdict` | `WIN` / `LOSE` |
| `complexity_cost` | 指令复杂度分项 |
| `beacon_cost` | 信标成本分项 |
| `time_cost` | 时间成本分项 |
| `total_score` | 最终得分 |
| `condition_count` / `action_count` / `beacon_count` / `elapsed_time` | 明细（FR-SCORE-05 要展示，便于核对） |
| `best_score` | 该关历史最佳（含本次如果刷新） |
| `is_new_record` | 本次是否刷新记录 |

### 3.3 系数配置（`res://data/scoring.json`）

```json
{
  "version": 1,
  "complexity": 10.0,
  "beacon": 10.0,
  "time": 1.0
}
```

| 键 | 对应 | 值 | 说明 |
|---|---|---|---|
| `complexity` | C1 | **10.0** | 指令复杂度系数 |
| `beacon` | C2 | **10.0** | 信标数量系数 |
| `time` | C3 | **1.0** | 时间系数 |

量级含义：**「1 条条件/行为」与「1 个信标」都等价于 10 秒时间**（D-14）。这样三个分项都有存在感——若 C1 太小（如 1.0），时间成本（秒）会淹没指令成本（个数），玩家只会追求快；若 C1 太大，玩家会不敢写多条指令，反而降低解法的丰富度。

> 这些系数是**起点而非终态**（D-14）。若实测发现「玩家只看时间」或「只看指令数」，改这个文件即可配平，**不用改代码**。

## 4. 算法

### 4.1 采集

```
# 结算时快照（不是每 tick 累加，因为规则表可能在编制期才最终确定）
snapshot_rules(units):
    for unit in units:
        for rule in unit.rules:
            if not rule.enabled:  continue
            condition_count += rule.conditions.size()
            action_count    += rule.actions.size()

snapshot_beacons(beacon_layer):
    beacon_count = beacon_layer.placed_count()      # 重置会清空重放，天然是「最新一次」

# 用时：直接取时钟
elapsed_time = clock.game_time
```

**为什么遍历全部启用指令而不是只统计生效的**：需求 10.1 已明确——否则「多写规则再用顺序覆盖」可以免费，评价体系会被绕过。

### 4.2 计算

```
compute(level_data, stats, coefficients) -> ResultData:
    complexity_cost = (stats.action_count + stats.condition_count) * coefficients.complexity
    beacon_cost     = stats.beacon_count                            * coefficients.beacon
    time_cost       = stats.elapsed_time                            * coefficients.time
    total_score     = complexity_cost + beacon_cost + time_cost
    best_score, is_new_record = save.update_best(level_data.id, total_score)
    return ResultData(...)
```

### 4.3 用时口径

`elapsed_time` 取 `clock.game_time`（= `tick_index * TICK_DELTA`），即**游戏内时间**：

| 好处 | 说明 |
|---|---|
| 与 FR-FLOW-06 一致 | 同一关用 1x 或 3x 通关，得分相同——倍速不影响结算结果 |
| 可复现 | 同一套规则跑出的 tick 数相同 → 得分相同，便于测试与比较 |

> 若策划要求「按真实耗时计」（即玩家用 3x 会占便宜），改为 `Time.get_ticks_msec()` 统计即可，本系统只需换一个取值来源（需求 12.4-④ 待定）。

### 4.4 最佳记录

- 键：`Save.data["best_scores"][level_id]`（int/float，取最低）。
- 首次通关即写入；之后仅当 `total_score < best_score` 才更新并置 `is_new_record = true`。
- 与现有 `Save` 的落盘时机一致：在关卡退出时 `Save.save_data()`，不每次结算都写盘。

### 4.5 失败时

`verdict == LOSE` → **不计算得分**、**不写记录**（FR-SCORE-06）；只返回一个仅含 `verdict` 的 `ResultData`，由系统 10 显示「重试 / 返回」。

## 6. 验收

### 6.1 冒烟测试用例

| 用例 | 断言 |
|---|---|
| 公式正确 | 构造 `(条件 3, 行为 2, 信标 4, 用时 10.0)` → `total = (2+3)*10 + 4*10 + 10*1 = 100` |
| 系数生效 | 把 C1 改为 20.0 → 复杂度分项翻倍，总分按预期变化（FR-SCORE-02） |
| 系数热调 | 重新载入 `scoring.json` → 无需重启即生效（FR-SCORE-03） |
| 只统计启用指令 | 一条含 2 条件 2 行为的指令被禁用 → 计数不含它（FR-SCORE-05 / FR-CMD-09） |
| 含被覆盖的指令 | 两条同类行为（后者覆盖前者）→ 两者**都**计入 | 
| 信标按最新一次 | 放 4 个 → 重置 → 放 2 个 → 计 2 |
| 用时与倍速无关 | 同一套规则分别在 1x 与 3x 通关 → `elapsed_time` 与 `total_score` 相同（**FR-FLOW-06 / FR-TEST-03**） |
| 首次记录 | 首次通关 → `best_score == total`，`is_new_record == true` |
| 刷新记录 | 第二次得分更低 → 更新；得分更高 → 最佳不变且 `is_new_record == false` |
| 失败不结算 | `verdict == LOSE` → 无分项、无得分、`Save` 未被修改 |
| 明细可核对 | `condition_count` / `action_count` / `beacon_count` / `elapsed_time` 与分项、总分算术一致 |

### 6.2 对应需求验收

| 需求编号 | 覆盖方式 |
|---|---|
| FR-SCORE-01 | `ResultData` 含三个分项与总分 |
| FR-SCORE-02 / 03 | 系数生效 + 热调 |
| FR-SCORE-04 | 最佳记录与刷新 |
| FR-SCORE-05 | 明细统计与算术核对 |
| FR-SCORE-06 | 失败不结算 |
| FR-FLOW-06 / FR-TEST-03 | 用时与倍速无关（得分一致） |

## 7. 风险与开放项

| 风险 | 说明 | 缓解 |
|---|---|---|
| 系数未配平导致分数无意义 | C1/C2 与 C3 的相对大小决定玩家追求什么 | 初值已定为 **C1=C2=10、C3=1**（D-14），即「1 条指令 ≈ 10 秒」；仍属可调区间，配平改 JSON 即可 |
| 用时口径切换 | 游戏内时间 vs 真实耗时会影响倍速的收益 | 已确认为**游戏内时间**（D-15），隔离在 4.3；改一处即可 |
| 统计时机 | 若每 tick 累加规则数，玩家在编制期改规则会导致计数漂移 | 采用「结算时快照」而非「每 tick 累加」（4.1） |
| 浮点比较 | 最佳记录用浮点相等判断可能永远刷不新 | 用 `total_score < best_score - 1e-6` 比较 |

**已关闭的待确认项**：

- ~~C1 / C2 / C3 的初值~~ → 已确认 **C1=10、C2=10、C3=1**（D-14）。
- ~~是否需要「达到某分数解锁下一关」~~ → 已确认**没有解锁门槛**（D-17），选关列表全部可进。
- ~~结算界面是否显示 S/A/B 评级~~ → 已确认**不做评级**（D-16），只显示分数与历史最佳。
