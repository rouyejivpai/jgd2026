## 1. 目标产物

### 1.1 一句话

单位是**没有智能的执行器**：持有自己的数值与规则表，每 tick 接收规则引擎产出的意图（[系统 02](02-规则引擎.md)），把它们落成**匀速直线移动**与**开火意图**，并在撞墙时干脆地停住。

### 1.2 交付物清单

| 交付物 | 形式 | 说明 |
|---|---|---|
| `UnitActor` | `unit/unit_actor.gd` | `CharacterBody2D` 主体：意图持有、碰撞、生命周期 |
| `Movement` | `unit/movement.gd` | 匀速直线推进 + 撞墙完全停止 |

> ### ⚠️ 两处实现方式与本文档原设计不同（已按实现更正）
>
> 原文列了两个独立交付物 `UnitStats`（`unit/unit_stats.gd`）与 `Health`（`unit/health.gd`）。
> **实现时两者都没有单独成类**，职责并入了 `UnitActor`：
>
> | 原设计 | 实际实现 | 为什么 |
> |---|---|---|
> | `UnitStats` 类 | `UnitActor.stats: Dictionary`，数值由 `DataLoader.get_unit_stats(type_id, overrides)` 产出 | 全程只有 `Dictionary` 一种用法（读字段、算 `effective_*`），再包一层类没有收益。**`unit_stats.gd` 从未被实现、也没有任何引用，已删除** |
> | `Health` 类 | `UnitActor` 上的 `hp` / `max_hp` / `is_slowed` / `is_dead` 字段 | 血量与减速只有这一个宿主，单独开类反而要到处转发。**`health.gd` 只是个写着「待实现」的空壳、没有任何引用，已删除** |
>
> 这两个文件曾长期留在仓库里且**头部写着「状态：待实现」**，
> 而对应任务（M2-8 / M3）其实早已完成 —— **会误导后来的人去重新实现一遍**。
> 现在加了一条守卫用例：生产代码里不允许再出现「待实现」的状态行。
| 单位视觉占位 | `UnitActor` 的子节点 | `Polygon2D` 方块 + 阵营配色（美术后置） |
| 自动化用例 | `tools/smoke_test.gd` 增量 | 见 6.1 |

### 1.3 三条行为契约

1. **没有意图就不动**：若规则引擎没给出移动意图，单位停在原地（不漂移、不抖动）。
2. **不做任何自主决策**（需求 FR-CBT-08）：不索敌、不规避、不寻路、不自动追击。
3. **撞到障碍完全停住**，不滑墙、不绕行（需求 FR-MAP-06 / D2）。

## 2. 系统边界

### 2.1 本系统负责

- 单位实体的创建、初始化（数值 + 阵营 + 初始位置）。
- 持有并应用意图：`target_beacon_index`（含到达切换）、`fire_mode`、`delay_remaining`。
- 匀速直线移动与撞墙停止。
- 血量、减速状态（层数）的存储与查询。
- 死亡标记、从 `BattleState` 注销、尸体视觉。
- 重置时恢复到初始状态。

### 2.2 本系统明确不负责

| 不负责 | 归属 |
|---|---|
| 决定「移动去哪」「开不开火」「延迟多久」 | [02 规则引擎](02-规则引擎.md) |
| 子弹生成、飞行、命中、伤害数值 | [05 战斗](05-战斗.md) |
| 目标选择（谁是最近敌人） | [03 网格地图](03-网格地图.md) 的 `BattleState` |
| 单位的**数值定义**（100 血、3 距离/秒） | [11 数据配置](11-数据配置.md) |
| 网格与障碍碰撞体的生成 | [03 网格地图](03-网格地图.md) |
| 血量条、减速图标的 UI 呈现 | [10 主界面与HUD](10-主界面与HUD.md) |
| 胜负判定 | [06 关卡数据与胜负条件](06-关卡数据与胜负条件.md) |

### 2.3 边界上的接口约定

- 本系统**只读取** `BattleState`，不改它（注册/注销除外）。
- 本系统**不生成**子弹：只把 `fire_mode` 暴露给系统 05，由系统 05 决定何时生成。
- 减速只**存储层数**，减速率（50%）由系统 05 施加、由本系统在移动时读取。

## 3. 数据结构

### 3.1 单位数值（`UnitStats`）

字段与 `res://data/units.json` 一一对应，并由关卡数据的 `overrides` 覆盖：

| 字段 | 类型 | 单位 | 说明 |
|---|---|---|---|
| `id` | `String` | — | 如 `standard_attack` |
| `name` | `String` | — | 显示名 |
| `max_hp` | `float` | 点 | 100 |
| `move_speed` | `float` | 距离/秒 | 3.0 |
| `can_attack` | `bool` | — | 基础人工生命为 `false` |
| `range` | `float` | 距离 | 3.0 |
| `damage` | `float` | 点 | 10.0 |
| `attack_interval` | `float` | 秒/发 | `1 / 攻速`；攻速 1 发/秒 → `1.0` |
| `projectile_speed` | `float` | 距离/秒 | 默认 12.0 |
| `projectile_radius` | `float` | 距离 | 默认 0.3（直径 0.6，需求 6.6） |
| `on_hit_status` | `String` | — | `""` 或 `"slowed"`（冰寒人工生命） |
| `vision_radius` | `float` | 距离 | `0` 表示取 `range`（需求 6.4 默认） |

**生效值（effective_*）**：单位对外只暴露 `effective_range` / `effective_vision_radius` / `effective_move_speed` 等**计算后**的值，规则引擎与战斗系统一律读这些，不读全局表。这样关卡级覆盖（第二、三关敌人射程覆盖为 2）自动生效（FR-UNIT-05）。

```
effective_move_speed = move_speed * (0.5 if slow_stacks > 0 else 1.0)   # 减速不叠加，见 4.5
effective_range      = range
effective_vision     = vision_radius if vision_radius > 0 else range
```

### 3.2 单位运行时状态（`UnitActor`）

| 字段 | 说明 |
|---|---|
| `entity_id` | 由 `BattleState` 分配的**升序** id（确定性依据） |
| `team` | `ALLY` / `ENEMY` |
| `stats` | `UnitStats` |
| `hp` | 当前血量 |
| `slow_stacks` | 减速状态（`is_slowed: bool`；只生效一层，见 4.5） |
| `is_dead` | 死亡标记 |
| `rules` | `Array[Rule]`，玩家的指令表；**归属玩家，重置时保留** |
| **意图** | |
| `beacon_sequence` | `Array[int]`，当前的目标信标序列（值拷贝） |
| `beacon_cursor` | 当前走到序列里的第几个 |
| `fire_mode` | `bool`，开火/停火意图（持续型） |
| `delay_remaining` | `float`，阻塞剩余秒数 |
| `was_blocked` | 本 tick 是否撞墙（调试与视觉用） |

### 3.3 碰撞与物理配置

| 节点 | 类型 | 层 | 掩码 | 说明 |
|---|---|---|---|---|
| `UnitActor` | `CharacterBody2D` | 1 | **2（仅障碍）** | 掩码不含 1 → **单位之间不碰撞** |
| `UnitActor/Shape` | `CollisionShape2D` | — | — | 矩形 `0.8 × 0.8` 格（需求 6.6） |
| `UnitActor/Hurtbox` | `Area2D` | 5 | 0 | 供子弹命中；不主动探测 |
| `UnitActor/Body` | `Polygon2D` | — | — | 视觉占位，阵营配色 |

> **层号约定**（概设 D8 的落地）：`1` 单位本体 · `2` 障碍 · `3` 我方子弹 · `4` 敌方子弹 · `5` Hurtbox。
> 阵营靠子弹层决定（我方子弹只掩码 `5`），不需要在代码里写 `if is_in_group("enemy")`。

## 4. 算法

### 4.1 应用意图（在 tick 顺序的第 3 步）

```
apply_intents(intent, tick_delta):
    1. 若 intent.delay_request 非空：
           delay_remaining = max(delay_remaining, intent.delay_request)   # 不叠加
    2. 若 intent.move_intent 非空：
           若 intent.move_intent.sequence 与 beacon_sequence 值相等：
               保持 beacon_cursor 不变                    # 关键：避免来回震荡
           否则：
               beacon_sequence = 序列值拷贝
               beacon_cursor = 0
    3. 若 intent.fire_intent 非空：
           fire_mode = intent.fire_intent
    4. delay_remaining = max(0, delay_remaining - tick_delta)
```

**第 2 步是规则引擎 4.3「值相等则保持序号」的落地处**，两处必须一致；改一处要改另一处。

> 注意第 4 步：延迟在**同一 tick 内**就减去一个步长，因此「延迟 1 秒」= 60 个 tick 的阻塞（第 1 个 tick 立刻扣掉一段）。tick 计数口径与系统 02 的 7.1 用例一致。

### 4.2 移动（在 tick 顺序的第 4 步）

> **实现已落地，两处与下面的初稿伪代码不同，以实际代码为准**（M1-4 被用例纠正）：
>
> 1. **到达判定不能当「够近就停」的宽容带。**
>    初稿用 `ARRIVE_EPSILON = 0.15` 做「距离 <= 阈值即到达」的判据，
>    结果单位一进入 0.15 范围就被判到达、**停在离信标 0.1 处**。
>    正确语义：**一步能跨到就精确吸附到信标中心**，否则继续匀速走；
>    阈值（现取 `0.001`）只用来识别「已经在信标上」这种等价情形。
> 2. **逻辑位置必须独立存储、按请求的位移累加，不能从像素反推。**
>    `global_position` 是 float32 像素，每步做一次 `global_position / tile_px`
>    会把尾数磨掉：最后一段残余（1e-3 格 = 0.06 px）直接归零，单位卡住不动。
>    撞墙时用 `col.get_travel()` 折回，保证逻辑坐标与像素不脱节。
>
> 因此 `Movement` 不再自己调物理，只提供纯算术的 `compute_step()`；
> 由 `UnitActor.step_movement()` 负责「精确吸附」与 `move_and_collide`。
> 另注：GD4 的属性 setter 里**没有** `field` 关键字，写成自身赋值又是递归，
> 所以位置字段不设 setter，改用 `set_logic_position()` 显式同步像素变换。

```
step_movement(tick_delta):
    was_blocked = false
    if delay_remaining > 0:  return                 # 阻塞：不动
    if beacon_cursor >= beacon_sequence.size():  return   # 没有目标：停在原地
    target = map.beacon_logic_position(beacon_sequence[beacon_cursor])
    to_target = target - position_logic
    if to_target.length() <= ARRIVE_EPSILON:        # 到达当前信标
        beacon_cursor += 1                          # 自动切下一个
        return                                      # 本 tick 不再移动
    step_len = effective_move_speed * tick_delta     # 匀速，无加减速
    if step_len >= to_target.length():
        motion_logic = to_target                    # 最后一段精确落到信标中心
    else:
        motion_logic = to_target.normalized() * step_len
    motion_px = motion_logic * TILE_PX
    var col := move_and_collide(motion_px)
    if col != null:
        was_blocked = true                          # 撞墙：只贴到碰撞点，不滑墙
```

要点：

| 点 | 说明 |
|---|---|
| `ARRIVE_EPSILON = 0.15` | 到达判定阈值（逻辑距离）。60 tick 下速度 2 的单位每 tick 走 `0.033`，远小于阈值，不会「越过信标」 |
| `move_and_collide` 而非 `move_and_slide` | **必须**：`move_and_slide` 会自动沿墙滑动，违反「撞墙完全停住」（需求 12.1） |
| 撞墙后不尝试绕行 | 不做寻路（D2）；下一 tick 仍朝同一信标直线推进，因此会持续贴着墙停下 |
| 精确落点 | 最后一段裁剪到目标距离，避免在信标附近来回抖动（FR-CMD-07 的「不抖动」） |
| 无目标时返回 | 保持位置，避免残留速度导致漂移 |

**「沿着墙滑」被明确禁止**：若实测发现 `move_and_collide` 在角落仍有微小偏移，改用在碰撞时把位置回退到碰撞点（`col.get_travel()`），不要引入滑动。

### 4.3 开火意图的暴露

本系统**不自己开火**，只提供 `wants_to_fire() -> bool`：

```
wants_to_fire():  return fire_mode and not is_dead and delay_remaining <= 0 and stats.can_attack
```

系统 05 每 tick 询问这个方法，再自行判定冷却、选目标、生成子弹。`delay_remaining > 0` 时返回 false —— 这就是「延迟期间也不开火」的落地处。

### 4.4 死亡与清理

```
die():
    if is_dead: return
    is_dead = true
    BattleState.unregister_unit(entity_id)     # 立刻退出一切查询
    EventBus.unit_died.emit(entity_id, team, position)
    Body.modulate = Color(0.45, 0.45, 0.5, 1.0)   # 变灰
    set_collision_layer_value(1, false)            # 尸体不再是障碍也不挡子弹
    Hurtbox.monitoring = false
    set_physics_process(false)                     # 不再移动
    # 节点保留到「重置关卡」或本局结束（需求 12.1a）
```

**尸体不参与任何逻辑**：因为它已从 `BattleState` 注销，视野、最近敌人、胜负统计都不会看到它。

### 4.5 减速【已确认：不叠加】

- 系统 05 命中时调用 `health.set_slowed()`，把 `is_slowed` 置为 `true`。
- **只有一层，不叠加**：已处于减速状态的单位再次被命中不改变任何东西（不会变得更慢）。
- 生效速度：`move_speed * 0.5` —— 严格按需求文档 6.3 的字面「降低 50%」。
- **没有持续时间**：一旦被减速就保持到本局结束。MVP 不引入状态计时器，因此不需要为「减速到期」再做一套 tick 递减逻辑。
- 重置关卡时清除。

> 为什么不做叠加：若每层再乘 0.5，两个冰寒单位就能把敌人压到 25% 速度，三个就基本锁死——「堆冰寒单位」会变成唯一的通关套路，而策划案里冰寒只是一个「攻击附带减速」的辅助单位。
>
> 若将来要做叠加与持续时间，改动集中在本节：把 `is_slowed: bool` 换成 `slow_stacks: int` + `slow_remaining: float`，并在 tick 里递减；`effective_move_speed` 换回叠加公式。

### 4.6 重置

```
reset():
    position = spawn_logic_position      # 回到关卡数据的初始坐标
    hp = stats.max_hp
    slow_stacks = 0
    is_dead = false
    fire_mode = false; beacon_sequence.clear(); beacon_cursor = 0; delay_remaining = 0
    恢复碰撞层与 Hurtbox 监控、恢复 _physics_process
    尸体外观回正
    # rules 与信标不清（需求 12.1a）
```

## 6. 验收

### 6.1 冒烟测试用例

| 用例 | 构造 | 断言 |
|---|---|---|
| 无意图不动 | 单位无任何规则，推进 120 tick | 坐标零变化 |
| 匀速直线 | 目标信标在正右方 3 格，速度 3 | 60 tick 后位移 ≈ 3.0 格（容差 0.02） |
| 到达即切换 | 序列 `1→2`，先到 1 | 到达 1 后 `beacon_cursor == 1`，目标变为信标 2 |
| 走完全部序列后停住 | 序列 `1`，到达后继续推进 120 tick | 停在信标 1 中心，不漂移、不绕圈 |
| 撞墙完全停止 | 墙在正前方，目标信标在墙后 | 单位停在墙前；位置**不再变化**，且不出现横向位移（验证没有滑墙） |
| 撞墙不穿墙 | 同上 | 中心始终在墙格之外 |
| 最后一段不抖动 | 目标距离小于一 tick 位移量 | 精确落在信标中心（误差 < 0.05），连续 10 tick 坐标不变（FR-CMD-07） |
| 延迟阻塞移动与开火 | `delay_remaining = 1.0`，且 `fire_mode = true`、有目标 | 60 tick 内不移动、`wants_to_fire()` 为 false；第 61 tick 恢复 |
| 单位互不碰撞 | 两个同阵营单位正面走向同一格 | 两者可以互相穿过，不会卡住 |
| 减速生效 | 命中带 `slowed` 状态的子弹后，速度变为 `move_speed * 0.5`；再次命中速度**不变**（不叠加） |
| 死亡后不参与查询 | 杀死一个敌人 | 它不再被 `query_nearest_enemy` 返回；尸体仍在场景树里 |
| 重置恢复 | 移动 + 受伤 + 死亡后 `reset()` | 位置、血量、状态复原；`rules` 保留 |

| FR-MAP-06 | 撞墙完全停止 / 不穿墙 / 不滑墙 |
| FR-CMD-07 / FR-TEST-02 | 无意图不动 + 最后一段不抖动 |

## 7. 风险与开放项

| 风险 | 说明 | 缓解 |
|---|---|---|
| 撞墙后「贴着墙抖动」 | 单位紧贴墙时每 tick 都撞，可能出现 1 像素级抖动 | 撞墙时若 `col.get_travel()` 长度接近 0，直接跳过位移；用例覆盖「位置不再变化」 |
| 到达判定与速度耦合 | 高速单位可能一步跨过信标 | 最后一段裁剪到目标距离（4.2），与速度无关 |
| 减速公式口径 | 需求写「降低 50%」，叠加与否会显著影响平衡 | **已确认不叠加、固定 50%、无持续时间**（D-06）；若将来要改，改动集中在 4.5 一节 |
| 尸体节点累积 | 尸体保留到重置，多波死亡后节点变多 | 教程三关规模无压力；若需要，上限保留 N 具后 `queue_free` 最旧的 |
| `beacon_sequence` 值拷贝 | 序列必须是值拷贝，否则撤回信标后单位行为会跟着变 | 应用意图时做 `Array.duplicate()`；用例覆盖「撤回信标后整条指令失效」 |
