## 1. 目标产物

### 1.1 一句话

`LevelSession` 是**一个关卡的总指挥**：读关卡 JSON → 装配地图/单位/信标 → 驱动「编制期 → 推演期 → 结算期」状态机 → 每个 tick 按固定顺序调用各系统 → 检查胜负。

### 1.2 交付物清单

| 交付物 | 形式 | 说明 |
|---|---|---|
| `LevelData` | `level/level_data.gd` | 关卡运行时数据类（与 JSON 一一对应） |
| `LevelSession` | `level/level_session.gd` | 状态机 + tick 编排 + 装配 + 重置 |
| `WinCondition` | `level/win_condition.gd` | 条件求值器（8 种条件类型 + 组间逻辑） |
| 关卡 JSON 格式 | 见 3.1 | 编辑器与运行时共用同一份 |
| 关卡清单 | `res://data/levels/manifest.json` | 手写清单：关卡 id 与顺序 |
| 教程三关数据 | `res://data/levels/tutorial_0{1,2,3}.json` | 见 3.3 |
| 自动化用例 | `tools/smoke_test.gd` 增量 | 见 6.1 |

### 1.3 交付物：一个关卡跑起来的完整链路

```
manifest.json → LevelData(校验) → BattleMap 建网格与碰撞体 → 生成单位
   → 信标层与信号表初始化 → 编制期（tick 不驱动逻辑）
   → 玩家点开始 → 推演期（每 tick 走 9 步） → 胜负达成 → 结算期
```

## 2. 系统边界

### 2.1 本系统负责

- 关卡 JSON 的载入、字段校验与错误定位。
- 关卡清单（`manifest.json`）的读取与顺序。
- 按关卡数据装配地图、双方单位、信标配额、信号数量。
- 会话状态机：编制期 / 推演期 / 结算期，以及失败态。
- **tick 编排**：按 9 步固定顺序调用各系统（见 4.2）。
- 胜负条件求值（8 种类型 + 组间「任一/全部」）。
- 重置关卡（清理边界按 [04](04-单位与移动.md) 4.6 与需求 12.1a）。
- 触发结算：把统计量交给系统 08。

### 2.2 本系统明确不负责

| 不负责 | 归属 |
|---|---|
| 评价公式与得分 | [08 评价与结算](08-评价与结算.md) |
| 关卡数据的**编辑**与存盘 | [07 关卡编辑器](07-关卡编辑器.md) |
| 单位的移动/战斗/规则求值 | 02 / 04 / 05 |
| 计时器与倍速 | [01 时间与逻辑帧](01-时间与逻辑帧.md) |
| 结算界面与关卡介绍界面 | [10 主界面与HUD](10-主界面与HUD.md) |
| 信标的**放置交互** | 信标层（`src/gameplay/beacon_layer.gd`）+ 系统 10 |
| 单位数值的默认值 | [11 数据配置](11-数据配置.md) |

### 2.3 边界上的接口约定

- 本系统是**唯一**调用「9 步编排」的地方；其它系统不得自行 `connect(clock.tick)`（见 [01](01-时间与逻辑帧.md) 4.3）。
- 本系统**不修改**单位内部状态，只调用各系统公开的 step 方法。
- 结算所需统计量由本系统**采集**（如用时、信标数），公式由系统 08 计算。

## 3. 数据结构

### 3.1 关卡 JSON 格式（`res://data/levels/*.json`）

```json
{
  "id": "tutorial_01",
  "name": "第一关 · 初识信标",
  "order": 1,
  "map": {
    "width": 7,
    "height": 7,
    "tiles": [[0,0,0,0,0,0,0], "..."]
  },
  "beacon_quota": 4,
  "signal_count": 3,
  "time_limit": 0,
  "units": [
    { "team": "ally",  "type": "standard", "pos": [1, 3],
      "overrides": {} },
    { "team": "enemy", "type": "basic_enemy", "pos": [5, 3],
      "overrides": { "range": 2 } }
  ],
  "win": {
    "logic": "any",
    "conditions": [
      { "type": "reach_position", "area": [[6,6]] }
    ]
  },
  "lose": {
    "logic": "any",
    "conditions": [
      { "type": "all_allies_dead" }
    ]
  },
  "intro": {
    "title": "第一关 · 初识信标",
    "tips": ["点击信标按钮，在地图上放下信标", "点击单位打开指令面板"]
  },
  "tags": [],
  "extra": {}
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `id` | ✅ | 唯一 id，与文件名一致 |
| `name` | ✅ | 选关界面显示名 |
| `order` | ✅ | 排序用（清单里也有顺序，以此为准做二次校验） |
| `map.width` / `map.height` / `map.tiles` | ✅ | 见 [03](03-网格地图.md) 3.1 |
| `beacon_quota` | ✅ | 玩家可放置的信标总数（需求 8.1「初始信标数」） |
| `signal_count` | ✅ | 信号数量；编辑器新建关卡默认 **3**（需求 12.1 决策） |
| `time_limit` | ⬜ | 秒；`0` 表示不限时（教程三关为 `0`） |
| `units[]` | ✅ | 每条：`team`、`type`、`pos`、`overrides` |
| `units[].overrides` | ⬜ | 单实例数值覆盖（如 `{"range": 2}`），见 FR-UNIT-05 |
| `units[].is_primary_target` | ⬜ | 默认 `true`；`false` 表示不计入「全歼」（见 3.2） |
| `win` / `lose` | ✅ | 见 3.2 |
| `intro.title` / `intro.tips` | ⬜ | 关卡介绍与 tips（需求 8.1，FR-TUT-03） |
| `tags` / `extra` | ⬜ | **兼容位**：原样保留、不做校验，供后续玩法扩展 |

`manifest.json`（手写清单，决定选关顺序）：

```json
{ "levels": ["tutorial_01", "tutorial_02", "tutorial_03"] }
```

### 3.2 胜负条件（8 种 + 组间逻辑）

| 类别 | `type` | 参数 | 判定 |
|---|---|---|---|
| 胜利 | `annihilate` | — | 敌方阵营中**所有 `is_primary_target == true`** 的单位均已死亡 |
| 胜利 | `reach_position` | `area: [[i,j], …]` | 任一**我方**单位中心所在的瓦片属于 `area` |
| 胜利 | `survive_until` | `seconds: float` | `time_limit` 或 `seconds` 到达时，指定单位仍存活 |
| 胜利 | `destroy_core` | `device_id` | 目标装置不存在（**MVP 不实现**，见 8.2） |
| 失败 | `all_allies_dead` | — | 我方阵营存活单位数为 0 |
| 失败 | `timeout` | — | `time_limit > 0` 且已用游戏时间 ≥ `time_limit`，且未达成胜利 |
| 失败 | `protected_died` | `unit_ref: int` | 指定单位死亡 |
| 失败 | `custom` | `expr: String` | **MVP 不实现**，留位 |

**组间逻辑**：`logic` 取 `"any"`（默认，任一满足）或 `"all"`（全部满足）。
**组内逻辑**：始终为「或」（条件表内任一条命中即该组达成）。

> 「与」的典型用例：`win.logic = "all"` + 条件 `annihilate` 与 `survive_until`，即「全歼且保核心存活」。

### 3.3 教程三关数据（需求 11 章）

| 关 | 地图 | `beacon_quota` | 我方单位 | 敌方单位 | `win` |
|---|---|---|---|---|---|
| `tutorial_01` | 7×7 | 4 | 基础人工生命（`standard`，无攻击） | **无敌人** | `reach_position`（格 `(4,1)`） |
| `tutorial_02` | 14×3 | 4 | 基础-攻击人工生命（`standard_attack`） | 基础 1 级敌人（`range` 覆盖为 2） | `annihilate` |
| `tutorial_03` | 7×7 | 6 | `standard_attack` + `ice`（冰寒） | 基础 1 级敌人（`range` 覆盖为 2） | `annihilate` |

三关的 `lose` 均为 `all_allies_dead`；`time_limit` 均为 `0`（不限时）。

> **第一关不放敌人**（D-02）。因此 `reach_position` 是第一关唯一的胜利条件，第一关也不会触发任何战斗逻辑——这让 M1 的最小闭环可以先用第一关验证「移动 + 信标」，再用第二关验证战斗。
>
> **关卡级覆盖只剩一处**：第二、三关的敌人射程都覆盖为 2（`units.json` 中为 5）。这也是 FR-UNIT-05 / FR-TEST-06 的验收用例。
>
> **第一关的几何约束（M1-7 实测得到的硬要求）**：目标格**可以通行、但不能放信标**
> （详设 03 的 2.3），而 `reach_position` 判定的是「单位中心所在瓦片」。
> 因此目标格必须落在**单位会走过去的路径上、且早于最后一个信标** ——
> 单位路过它时立刻判胜。第一关据此把目标格设在 `(4,1)`：单位从 `(1,1)` 向右
> 走向信标 `(6,1)` 的途中会经过它。
> **不要**把目标格放在最后一个信标之后：单位一到最后一个信标就停住，
> 永远不会踏上那个格子（这正是 M1-7 一开始失败的原因）。

## 4. 算法

### 4.1 载入与校验顺序

```
载入 LevelData(json):
    1. 校验必填字段与类型           → 缺失/类型错 → 报错含字段路径
    2. 校验 map.tiles 尺寸与取值     → 报错含「第 j 行第 i 列」（系统 03）
    3. 校验 units[].type 在 units.json 中存在
    4. 校验 pos 在地图内、且落点瓦片可通行
    5. 校验 win/lose 的 type 合法、参数齐全（area 坐标在地图内）
    6. 校验 time_limit 与 survive_until 参数互不矛盾
任何一步失败 → 载入失败，游戏给出「哪个文件、哪个字段、什么问题」，不静默降级
```

### 4.2 tick 编排（9 步，必须显式调用）

```
func _on_clock_tick() -> void:
    signal_store.commit()                  # 1. 上一 tick 的信号生效（D4）
    rule_engine.evaluate_all()             # 2. 逐单位求值 → Intent
    units.apply_intents(tick_delta)        # 3. 应用意图 + 延迟递减
    units.step_movement(tick_delta)        # 4. 直线移动、撞墙停止
    combat.step_weapons(tick_delta)        # 5. 冷却、选目标、生成子弹
    combat.step_projectiles(tick_delta)    # 6. 子弹推进、命中、伤害
    battle_state.cleanup_dead()            # 7. 清理死亡（尸体保留，只注销）
    var verdict := win_condition.evaluate()
    if verdict != NONE:  end_session(verdict)   # 8. 胜负检查
    statistics.sample()                    # 9. 统计采样
```

**顺序契约**：这 9 步的先后由本系统固定，**不通过信号订阅顺序实现**（Godot 信号回调顺序不可依赖）。

### 4.3 会话状态机

| 状态 | 进入动作 | 退出动作 |
|---|---|---|
| `BUILD`（编制期） | 时间冻结；连接信标层与指令面板；弹关卡介绍一次 | 点开始时退出 |
| `RUN`（推演期） | 开始订阅 `clock.tick`；`clock.tick_index = 0` | 胜负达成或失败时退出 |
| `RESULT`（结算期） | 断开 `tick`；计算评价；写最佳记录 | 重试 / 下一关 / 返回选关 |

**编制期不驱动逻辑的实现方式**：本系统在 `BUILD` 期间**不连接** `clock.tick` 到 `_on_clock_tick`。`GameClock` 本身不知道编制期的存在（见 [01](01-时间与逻辑帧.md) 3.3）。

### 4.4 重置（按需求 12.1a）

```
清空：单位位置/血量/状态、全部子弹、信号表（全关）、延迟计时器、
      tick 计数与统计、尸体外观回正、`BattleState` 重建
保留：玩家的指令（单位 rules）、信标放置、倍速设置、关卡数据本体
```

### 4.5 胜负求值的触发时机

每 tick 第 8 步调用一次（不是只在「有单位死亡」时）。理由：`reach_position` 与 `timeout` 与死亡无关，必须每 tick 检查。求值是纯读操作，代价可忽略。

## 6. 验收

### 6.1 冒烟测试用例

| 用例 | 断言 |
|---|---|
| 三关全部可载入 | `tutorial_01/02/03` 载入无错，地图尺寸、单位数、`beacon_quota` 与 3.3 表一致 |
| 校验：tiles 尺寸错 | 行数少一行 → 报错含行号，载入失败 |
| 校验：单位类型不存在 | `type: "nope"` → 报错含字段路径 |
| 校验：坐标越界 | `pos: [99,99]` → 载入失败 |
| 校验：坐标落在障碍上 | `pos` 指向瓦片 1 → 载入失败 |
| 第一关无敌人仍可通关 | `tutorial_01` 载入后敌方阵营为空；单位走进终点格 → 判胜利（D-02） |
| `manifest.json` 顺序 | 选关列表顺序 = 清单顺序 |
| 编制期时间冻结 | 进入 `BUILD` 后推进 600 个 clock tick | 单位坐标与信号表零变化（FR-FLOW-01） |
| 开始后推进 | `start()` 后推进 60 tick | `tick_index` 相关统计与单位行为符合预期（FR-FLOW-02） |
| 关卡级覆盖生效 | 第二关敌人 `effective_range == 2`（第三关同为 2），而 `units.json` 中为 5（FR-UNIT-05 / FR-TEST-06） |
| 全歼条件 | 第一关式的 `annihilate`：杀死全部 `is_primary_target` 敌人 → 判胜利 |
| 全歼不计非目标 | 将一个敌人 `is_primary_target = false`，杀光其余 → 仍判胜利 |
| 到达条件 | 单位走进 `area` 指定格 → 判胜利 |
| 全灭条件 | 我方全部死亡 → 判失败 |
| 超时条件 | `time_limit = 30`，挂机 30 秒游戏时间 → 判失败 |
| 组间「与」 | `logic = "all"` 且两个条件，仅满足其一 → 不判胜利 |
| 重置保指令与信标 | 改动指令与信标后 `reset()` → 两者保留，单位位置与血量复原（FR-FLOW-04） |
| 编排顺序 | 用可观测副作用（信号次 tick 生效）断言 9 步顺序正确 |

## 7. 风险与开放项

| 风险 | 说明 | 缓解 |
|---|---|---|
| `tiles` 巨大导致 JSON 冗长 | 大地图时数组很长 | 教程三关最大 14×3，无影响；若将来需要，`extra` 里可放压缩表示并由关卡层自定义解析 |
| 编排顺序被无意改动 | 有人把某系统改成自行订阅 tick，玩法会静默改变 | 4.2 明确「唯一编排点」；用例「编排顺序」守护 |
| 编辑器保存的关卡载入失败 | 编辑器与运行时的校验口径必须一致 | 编辑器保存前调用**同一个** `validate()`（见 [07](07-关卡编辑器.md)） |
| `survive_until` 与 `time_limit` 语义重叠 | 两者都可能引入倒计时 | `time_limit` 是全局上限（也用于 `timeout` 失败）；`survive_until.seconds` 是条件自己的计时。MVP 三关都不使用 |
| 写入 `res://` 的限制 | 编辑器保存到工程目录在导出后不可写 | 见 [07](07-关卡编辑器.md) 4.4 的回退策略 |

**已关闭的待确认项**：

- ~~第一关的敌人该不该开火？~~ → 已确认**第一关不放敌人**（D-02）。
- ~~`reach_position` 的 `area` 是格列表还是矩形范围？~~ → **格列表**：编辑器把「刷成目标区域（瓦片 2）的格子集合」自动同步进 `area`（见 [07](07-关卡编辑器.md) 4.1）。字段结构为 `"area": [[i,j], …]`。

**仍开放**：无。本系统的设计已无待决项。
