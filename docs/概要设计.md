## 1. 架构总览

### 1.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│ 表现层  src/ui/       指令编辑抽屉 · 主界面 HUD · 关卡介绍 · 结算 │
│         src/editor/   关卡编辑器（独立场景）                     │
├──────────────────────────────────────────────────────────────┤
│ 流程层  src/gameplay/ 关卡会话状态机 · 场景装配 · 相机 · 辅助显示  │
├──────────────────────────────────────────────────────────────┤
│ 逻辑层  src/core/     规则引擎 · 时间系统 · 网格地图 · 单位与移动  │
│                       · 战斗 · 胜负条件 · 评价                   │
├──────────────────────────────────────────────────────────────┤
│ 数据层  src/core/data/ 单位表 · 布局表 · 评价系数 · 关卡数据       │
│         data/*.json    静态配置（策划可直接改）                   │
├──────────────────────────────────────────────────────────────┤
│ 内核    autoload/      EventBus · Game · Audio · Save · SceneLoader │
│         （已就绪，原则上不改）                                    │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向自下而上**：逻辑层不依赖表现层；`src/core/` 内的模块**不引用任何场景节点路径**，只通过参数与返回值交互，便于在 `smoke_test` 里直接构造与断言。

### 1.2 关键架构决策（已确认）

| # | 决策 | 影响 |
|---|---|---|
| D1 | 逻辑 tick = **固定 1/60 秒步长累加器**，与倍速无关；倍速只改变每个渲染帧累加多少游戏时间 | 倍速一致性（FR-TEST-03）成立的前提 |
| D2 | **不做寻路**。单位直线走向目标信标，撞到障碍**完全停住** | 不能用 `move_and_slide`（会滑墙），改用 `move_and_collide` |
| D3 | 单位**不做任何自主决策**：不索敌、不规避、不寻路。视野只用于条件求值；开火时引擎自动取最近敌人 | 规则引擎可做成无状态求值 |
| D4 | 信号在**下一 tick** 才被条件读到 | 求值顺序完全确定，可复现 |
| D5 | 「延迟」是**阻塞型计时器**，不参与冲突键覆盖 | 规则引擎多一条处理路径（见 D2 详设） |
| D6 | 静态数据走 **JSON**，运行时状态用**带类型提示的 GDScript 类** | 改数值不用重启；有静态检查与单测 |
| D7 | 编辑器 UI **用代码构建 Control**，不用 .tscn 手摆 | 属性面板可按数据动态生成 |
| D8 | 碰撞分层：1 单位本体 / 2 障碍 / 3 我方子弹 / 4 敌方子弹 / 5 我方 Hurtbox / 6 敌方 Hurtbox | 阵营判断交给物理层，不写 `is_in_group`；Hurtbox 按阵营拆两层是为了让「子弹不伤害友军」由掩码免费保证（详见 [05 战斗](design/05-战斗.md) 第 3 章） |
| D9 | 事件总线**按性质分流**：流程与 UI 关心的事件走 `EventBus`，高频内部状态不出系统 | 避免指令系统每帧喷信号 |
| D10 | 关卡数据为 `res://data/levels/*.json`；信号与信标数**不设全局上限**，由关卡数据定 | 编辑器与运行时读同一份文件 |

## 2. 跨系统约定

### 2.1 逻辑 tick 与时间

| 约定 | 内容 |
|---|---|
| tick 步长 | 固定 `1.0 / 60.0` 秒游戏时间 |
| 驱动 | `_physics_process(delta)` 中累加 `delta * speed_multiplier`，满一个步长执行一次 tick |
| tick 内顺序 | ① 规则评估 → ② 落地意图 → ③ 移动 → ④ 开火与冷却 → ⑤ 子弹推进与命中 → ⑥ 死亡清理 → ⑦ 胜负检查 → ⑧ 信号提交（下一 tick 生效） |
| 禁止 | 任何逻辑不得直接读 `delta` 做数值积分；一律用固定步长 |
| 幂等性要求 | 同一 tick 内重复调用评估不得改变结果 |

### 2.2 坐标与单位

- 1 瓦片 = 1 距离；瓦片 `(i, j)` 中心的世界坐标 = `(i * TILE_PX, j * TILE_PX)`，`TILE_PX` 为渲染用像素尺寸（默认 64）。
- 逻辑层一律用**格坐标（浮点）**，只在渲染层乘 `TILE_PX`。
- 距离用欧氏距离。

### 2.3 事件总线使用规范（D9）

| 走 `EventBus`（流程与 UI 关心） | 不出系统（高频内部状态） |
|---|---|
| 关卡开始 / 胜负判定 / 评价变化 / 单位死亡 / 信号变化 / 信标变化 | 单位位置、朝向、子弹位置、冷却剩余、意图刷新 |

新增信号统一加在 `autoload/event_bus.gd`，命名 `蛇形_过去式`（如 `unit_died`），并在该文件顶部补注释说明谁发谁收。

### 2.4 命名与代码约定

- 文件与目录 `蛇形命名`；类名 `PascalCase`；常量 `UPPER_SNAKE`。
- 逻辑层类一律 `class_name` 注册，便于单测与跨模块引用。
- 数值**不出现魔法数字**：一律从 `DataLoader` 取，或写成具名常量。
- 每份详设第 1 章为「目标产物」，第 2 章为「系统边界」，与用户要求一致。

### 2.5 测试约定

- 纯逻辑（`src/core/`）用 `tools/smoke_test.gd` 直接构造并断言，不依赖渲染。
- 涉及物理与碰撞的（子弹命中、撞墙停止）用**无头运行 + 手动推进 tick**的方式断言，不靠肉眼。
- `smoke_test` 输出 `全部通过 ✅` 且退出码 0 才算通过（现有 52 项检查）。

## 4. 数据流

### 4.1 编制期

```
关卡 JSON ──DataLoader 校验──> LevelData ──LevelSession 装配──> 地图/单位/信标 就绪
                                                                    │
   玩家点单位 ──> 指令编辑抽屉（系统 09）── 编辑 Rule 列表 ──写回──> 单位(UnitActor).rules
                                                                    │
   玩家放信标 ──> BeaconLayer（系统 03）──> 信标序列 + 全局信号表（初始全关）
```

**编制期时间不推进**：系统 01 的累加器不累加，任何逻辑 tick 都不执行。

### 4.2 推演期（每个逻辑 tick 的执行顺序）

```
系统01 触发 tick
  └─ 系统02 规则引擎：逐条求值 ──> 生效行为集合
        ├─ fire_mode  ──> 系统04 置开火意图
        ├─ move       ──> 系统04 置目标信标
        ├─ signal:<n> ──> 写入「待提交」信号表（下个 tick 生效，D4）
        ├─ delay      ──> 系统04 置阻塞计时器（D5）
        └─ interact   ──> 【MVP 不实现】
  └─ 系统04 应用意图：延迟阻塞则跳过移动/开火 → move_and_collide 直线推进（撞墙即停）
  └─ 系统05 战斗：冷却判定 → 生成子弹（自动选最近敌人）→ 子弹推进 → 命中结算 → 死亡清理
  └─ 系统06 胜负条件求值（每次单位死亡/到达/超时后）
  └─ 系统08 记录统计量（条件数/行为数/信标数/耗时）
  └─ 信号表提交（本 tick 写入的信号在此刻正式生效）
```

### 4.3 结算与编辑器

```
胜负达成 ──> 系统08 评价 ──> UI 结算界面（系统 10）── 写最佳记录 ──> Save（autoload）
编辑器（系统 07）── LevelData 编辑 ── LevelIO 保存 ──> res://data/levels/*.json
       └─ 「试玩」────> 直接载入系统 06 进入编制期
```
