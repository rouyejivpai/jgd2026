## 1. 概述

### 1.1 一句话定位

**实时战术解谜**：玩家不直接操作单位，而是战前为每个单位编制一套「如果…则…」指令规则，按开始后用规则间接指挥，靠规则设计过关。

### 1.2 世界观与题材（已定）

- 玩家扮演试图完成炼金术终极目标的**炼金术士**，目标是创造具有智慧的人工生命。
- 她发现造物只会执行指令、没有智能，但通过训练能让智能在某个临界点涌现，于是不断训练下去。
- 美术风格：**西方神秘学 / 炼金术魔幻**。
- 策划案说明：多数 UI 取自《异常》游戏截图，作为布局参照，**不直接复用素材**。

### 1.3 平台与运行环境

| 项 | 要求 |
|---|---|
| 目标平台 | PC（Windows）；手机端不在 MVP，仅在不影响架构的前提下保留可能性 |
| 分辨率 | 沿用工程策略：1920×1080 视口 + `canvas_items` 拉伸 + `expand` 宽高比 |
| 引擎/语言 | Godot 4.7.2 stable、GDScript（无 C#） |

### 1.4 核心乐趣（决定优先级排序的依据）

1. **编制期**的规则设计：把「全歼敌人」翻译成一组不冲突的条件-行为。
2. **推演期**的观察：按开始后看自己的规则跑起来，失败要能复盘出「哪条规则写错了」。
3. **优化期**：同一关用更少的指令、更少的信标、更短的时间通过，换取更高评价。

评价体系（第 10 章）就是围绕第 3 点设计的，**优先级高于任何视觉打磨**。

### 1.5 非目标（MVP 明确不做）

- 不做玩家实时操作单位的 RTS 式操作；点选单位只用于打开指令编辑界面。
- 不做联机、不做存档中途保存战场（只存关卡进度与评价）。
- 不做第一章及以后的剧情、关卡、新装置（Phase 2）。
- 不做手机端适配与触屏 UI。

## 3. 系统总览与流程

### 3.1 关卡状态机

```
载入关卡 → 编制期（时间静止）→ 推演期（时间流动）→ 结算期 → 返回选关/下一关
                ↑                      ↓
                └────── 重置关卡 ───────┘
```

| 状态 | 时间 | 玩家可做什么 | 玩家不可做什么 |
|---|---|---|---|
| 编制期 | 完全静止 | 编辑指令、放置/撤回信标、查看关卡介绍与机制说明、调倍速设置 | 单位不动、不射击、不结算 |
| 推演期 | 实时流动 | 只能调倍速、查看信息 | **不可暂停编辑指令**、不可移动信标 |
| 结算期 | 停止 | 查看评价、重试、返回 | 继续操作战场 |

### 3.2 功能需求

| 编号 | 功能点 | 优先级 | 验收方式 |
|---|---|---|---|
| FR-FLOW-01 | 关卡载入后进入编制期，时间不推进 | P0 | 进入关卡后停留 30 秒，所有单位位置与状态不变 |
| FR-FLOW-02 | 点「开始」进入推演期，时间开始流动 | P0 | 点开始后单位按指令行动 |
| FR-FLOW-03 | 推演期提供 1x / 2x / 3x 倍速切换 | P1 | 切 3x 后同样的指令跑完耗时约为 1x 的 1/3 |
| FR-FLOW-04 | 「重置关卡」回到该关初始状态，**已编写的指令与信标保留** | P0 | 推演失败后重置，指令列表与信标位置与重置前一致 |
| FR-FLOW-05 | 满足胜利条件进入结算期，满足失败条件判定失败 | P0 | 见 9.3 与 11 章 |
| FR-FLOW-06 | 倍速通过**自持的游戏时间乘数**实现（`GameClock`），**不得**影响指令评估顺序与结算结果 | P0 | 同一关在 1x 与 3x 下的胜负与评价一致（见 FR-TEST-03）。**注意**：不用 `Engine.time_scale`，因为它已被顿帧占用（见 [详设 01](design/01-时间与逻辑帧.md) 2.3） |

## 4. 地图与坐标系

### 4.1 坐标系定义

- 底图为正方形瓦片网格。**横轴为 x 轴，纵轴为 y 轴**（策划案 2.1 原文）。
- 网格原点在地图左上角，x 向右递增，y 向下递增（与 Godot 2D 屏幕坐标一致，避免转换分支）。
- **瓦片中心坐标为整数**：瓦片 `(i, j)` 的中心 = `(i, j)`；因此 1 瓦片 = 1 距离，相邻瓦片中心距离恒为 1。
- 单位位置使用**连续浮点坐标**，不必落在瓦片中心。
- 距离一律取欧氏距离：`dist = sqrt(dx² + dy²)`。
- 策划案 2.1 的坐标系示意图可作为视觉参照：[`_refs/media/img001.png`](../../_refs/media/img001.png)（2559×1439，同时用作 3.1 主玩法示意图）。

### 4.2 瓦片类型

| 类型 | 可通行 | 可放置信标 | 说明 |
|---|---|---|---|
| 空地 | ✅ | ✅ | 默认地形 |
| 障碍 / 墙 | ❌ | ❌ | 阻挡移动；**不阻挡视野**（见 6.4） |
| 目标区域 | ✅ | ❌ | 终点类胜利条件的判定区域 |

> **出生点瓦片类型已取消**（见 [概要设计 D 决策](概要设计.md) 与 [详设 03](design/03-网格地图.md) 2.3）：单位初始位置直接写在关卡数据的单位条目里。理由：一个格子可以同时是「目标区域」且站着一个单位，不会互斥；编辑器也少一道「先刷出生点再放单位」的工序。

### 4.3 功能需求

| 编号 | 功能点 | 优先级 | 验收方式 |
|---|---|---|---|
| FR-MAP-01 | 关卡数据可定义地图尺寸与每格类型 | P0 | 载入 7×7 与 14×3 两种尺寸均正确渲染与移动 |
| FR-MAP-02 | 1 瓦片 = 1 距离，瓦片中心为整数坐标 | P0 | 相邻格中心距离断言 = 1.0 |
| FR-MAP-03 | 信标只能放置在「可通行且可放置」格 | P0 | 往障碍格放信标时被拒绝且给出反馈 |
| FR-MAP-04 | 同一格允许多个信标（重复放置） | P1 | 同一格放两个信标均成功，且序号分别为 1、2 |
| FR-MAP-05 | 地图可能存在特殊装置 | P2 | 装置类型待策划补充，先预留数据结构 |
| FR-MAP-06 | 单位直线走向目标信标，**不做任何寻路**；撞到障碍即完全停住 | P0 | 把信标放在墙后，单位走到墙前停住；不会穿墙、不会自己绕行 |

## 5. 指令系统【核心】

指令是玩家与单位之间**唯一**的交互手段。本节是整个项目的最高风险点，建议先做一个只含移动与开火的最小闭环来验证语义（见 FR-TEST-01）。

### 5.1 指令的数据结构

```
Rule {
  enabled : bool           # 是否启用（见 FR-CMD-09）
  conditions : Condition[] # 0..n 个条件
  condition_logic : AND | OR
  actions : Action[]       # 1..n 个行为，同类型行为只允许一个
}
```

### 5.2 条件（Condition）类型

| 类型 | 参数 | 说明 |
|---|---|---|
| 视野内出现敌人 | 半径 `radius`【默认：单位当前攻击射程】 | 见 FR-CMD-02 |
| 信号状态 | 信号编号、目标状态（开/关） | 例：信号 1 开 |
| 与某信标距离 | 信标编号、比较符（< / ≤ / = / ≥ / >）、距离值 | 例：距离信标 1 ≤ 2 |
| 血量状态 | 比较符、百分比 | 例：血量低于 60% |
| 敌人持有 / 不持有某状态 | 状态类型（如减速） | 例：敌人处于减速状态 |
| 其他 | — | 策划案标注「待补充」，见 12.7 |

**组合**：条件之间可区分「与（同时满足）」和「或（满足其中一项）」（策划案 3.3.2）。一条指令只使用一种逻辑（要么全与、要么全或），不做嵌套——嵌套留到 Phase 2。

### 5.3 行为（Action）类型

| 类型 | 参数 | 说明 |
|---|---|---|
| 开火模式 | 开火 / 停火 | 二选一，互斥 |
| 移动模式 | 信标序列，如 `1→2→3` | 沿指定信标顺序移动 |
| 信号 | 信号编号 + 设为开/关 | 所有信号初始为关 |
| 延迟时间 | 秒数 | 例：停止 1/2/3 秒 |
| 与装置互动 | 装置编号 + 交互类型 | 充能 / 按下按钮等，装置待补充 |
| 其他 | — | 策划案标注「待补充」，见 12.7 |

### 5.4 执行语义【已确认】

每个逻辑帧执行以下流程：

1. 从第 1 条指令开始，按顺序向下逐条评估条件。
2. 收集**所有**「条件成立」且 `enabled == true` 的指令。
3. 按**行为冲突键**分组，每组只保留**顺序最靠后**的那条指令的行为生效（后面的覆盖前面的）。
4. 执行最终生效的全部行为；不相冲突的行为**同时生效**。

**冲突键**定义（同类行为互斥的判定依据）：

| 冲突键 | 互斥行为 |
|---|---|
| `fire_mode` | 开火、停火 |
| `move` | 不同的移动目标 |
| `signal:<n>` | 对同一信号编号的置开 / 置关 |
| `interact:<device>` | 对同一装置的不同交互 |

> `delay` 不在上表内：它是阻塞型计时器，不参与冲突覆盖，见下方说明。

**策划案原文示例的验证**：第 1 条为「无条件 · 停火」，第 2 条为「视野中出现敌人 · 开火」。有敌人时两条都成立，`fire_mode` 冲突，顺序靠后的第 2 条胜出 → 最终效果是**有敌人时开火**。与策划案 3.3.2 的描述完全一致。✅

**持续型行为的保持**：`move` 与 `fire_mode` 属于状态型行为。当某一帧所有指令都不再产生 `move` 时，单位应**保持**上一次的移动意图（继续走向当前目标），而不是停在原地抖动；`fire_mode` 同理保持。条件转假只意味着「不再刷新这个意图」，不等于「撤销」。**撤销必须由一条显式行为完成**（例如把开火模式切回停火）。

> 这条是「按开始后看规则跑起来」是否可读的关键。若实现成「条件不成立就清空意图」，策划案示例还能对，但玩家的其它写法会莫名其妙失效。

**「延迟」是阻塞型行为，不参与冲突覆盖**：延迟是一个逐 tick 递减的计时器。计时器未走完期间，单位**原地不动、也不开火**，无论移动与开火意图是否被刷新；计时结束后自动解除阻塞，恢复执行当时的移动与开火意图。因此 `delay` 不占用 `move` / `fire_mode` 的冲突键（见 5.4 冲突键表已作相应调整）。

## 6. 战斗规则

### 6.1 攻击流程

1. 单位处于开火模式且目标合法时，按攻速间隔发起攻击。
2. 生成**有飞行时间的实体投射物**，命中判定使用碰撞体（`Area2D` + 层/掩码）。
3. 投射物命中敌方单位 → 造成伤害；撞到障碍、或飞满射程即销毁。
4. 攻速以「发/秒」为配置单位，内部换算为 `射击间隔 = 1 / 攻速`。

### 6.2 命中与目标选择

| 项 | 规则 |
|---|---|
| 命中判定 | 实体投射物 + 碰撞体，**不做**瞬时命中 |
| 单位是否自己选目标 | **否**。单位不做任何自主决策；「视野」只用于条件求值，是否开火完全由玩家的开火/停火指令决定 |
| 开火时的目标 | 开火指令生效时，由引擎自动取视野内的**距离最近**敌人（见 6.4） |
| 距离相同时 | 取编号更小（或生成更早）者，保证结果确定 |
| 目标死亡 | 立即重新选择目标 |
| 视线遮挡 | 不做视线遮挡判定（见 D-05） |

### 6.3 伤害与状态

- 伤害为固定值扣血，暴击/护甲/减免不在 MVP（见 D-05）。
- **减速**：使目标移动速度降低 **50%**（策划案 3.5.1 第 4 项）。**不叠加**——已处于减速状态的单位再次被命中不改变效果，因此不支持「靠堆冰寒单位锁死敌人」。
- 减速**没有持续时间**：一旦被减速就保持到本局结束（重置关卡时清除）。原因：MVP 不引入状态计时器，避免为「减速到期」再做一套 tick 递减逻辑。
- 血量归零即死亡，从场上移除。

### 6.4 视野

- 视野 = 以单位为圆心的**半径圆**，**不受墙体遮挡**。
- 视野半径默认取该单位的攻击射程（见 D-05）。策划案图 1 中单位周围的圆形范围即为该表现。
- 视野有两个用途：① 给「视野内出现敌人」条件求值；② 开火时确定候选目标范围。**单位本身不记忆、不追踪任何目标**。

### 6.5 子弹参数【已确认】

| 参数 | 值 | 说明 |
|---|---|---|
| 子弹飞行速度 | 12 格/秒 | 写进 `units.json`，逐单位可覆盖 |
| 销毁条件 | 飞满射程 / 撞障碍 / 命中目标 | 三者任一即销毁 |
| 命中盒直径 | 0.6 格 | 子弹的碰撞圆直径 |
| 单位碰撞盒 | 0.8 格 × 0.8 格 | 单位占据的方形碰撞体 |
| 目标中途死亡 | 子弹**继续沿原方向飞**，可能命中后面的敌人 | 子弹无状态、不记忆目标（见 12.1） |

## 10. 评价与结算

### 10.1 评价公式（策划案 3.6）

```
指令复杂度 = (行为数量 + 条件数量) × C1
信标成本   = 信标数量 × C2
时间成本   = 所用时间 × C3
最终得分   = 指令复杂度 + 信标成本 + 时间成本      # 越低越好
```

| 符号 | 含义 | 值 |
|---|---|---|
| C1 | 指令复杂度系数 | **10**（见 D-14） |
| C2 | 信标数量系数 | **10** |
| C3 | 所用时间系数 | **1** |

量级含义：**「1 条条件/行为」与「1 个信标」都等价于 10 秒时间**，因此三个分项都不会被彼此淹没——玩家既不能只靠堆时间、也不能只靠少写指令来刷分。

统计口径（需实现一致）：

- 「行为数量」「条件数量」统计**全部已启用指令**中累计的条件与行为个数，含被覆盖而未生效的指令（否则「多写规则再覆盖」可以免费）。
- 「信标数量」统计**本局实际放置**的信标数（重置后重新放置则按最新一次计算）。
- 「所用时间」统计从点开始到结算的时间，**按游戏内时间**（见 D-15：因此同一关用 1x 或 3x 通关得分相同）。

> ⚠️ 策划案原文写作「信标数量=信标数量×系数」，存在自我引用，本文件按上表理解为「信标成本 = 信标数量 × 系数」（见 D-10）。

### 10.2 功能需求

| 编号 | 功能点 | 优先级 | 验收方式 |
|---|---|---|---|
| FR-SCORE-01 | 结算界面展示三个分项与最终得分 | P0 | 通关后三项数值与总分可见且可核对 |
| FR-SCORE-02 | 三个系数来自 `res://data/scoring.json` | P0 | 改系数后重跑同一关，分数按新系数变化 |
| FR-SCORE-03 | 系数支持热调，便于配平 | P1 | 不重开游戏即可应用新系数 |
