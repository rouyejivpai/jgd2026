## 1. 场景分层：玩法地面与纯背景（A17）【会议已定方向】

### 1.1 概念

| 层 | 内容 | 交互 | 绘制范围 |
|---|---|---|---|
| **Backdrop 纯背景** | 整幅 1920×1080 画面：远景、建筑立面、竖墙、树干、石柱等一切竖立景物，以及玩法区四周的环境 | 无 | 全屏，在 UI 之下 |
| **Playfield 玩法地面** | 网格、可行走格、障碍格的**地面标识**、部署区、路线、信标、单位 | 全部输入只在此矩形内有效 | 固定矩形，见 1.2 |

规则：
- 玩法矩形内**不画任何竖立物**。障碍格用地面标识表现：平铺的碎骨/裂地/血渍贴片（`biomes.json` 的 `ground_marks`），规划状态下叠红色斜纹，平时弱显示。
- 原 `PropsLayer` 的墙/荆棘/骨桩等竖立道具**停用**（素材保留，可放进纯背景区由美术合成）。
- 镜头不再缩放到"地图铺满可视区"。Backdrop 始终铺满窗口（`stretch canvas_items` 下即 1920×1080 设计分辨率），Playfield 按 1.2 的固定矩形绘制。窗口比例变化时 backdrop 按 `expand` 规则裁边，玩法矩形居中不变。
- 网格、部署区、路线、信标、MapInput 的命中测试都用 Playfield 矩形裁剪；矩形外的点击一律视为"点击空地"。

### 1.2 玩法矩形的计算（程序与资源共用）

战场可视区为 y∈[64, 960]（顶栏 64px，底栏 120px），玩法区最大 1600×800，居中于 (960, 512)。
`cell_px = floor(min(1600 / W, 800 / H))`，矩形 = 以 (960,512) 为中心、`W*cell_px × H*cell_px`。

| 关 | 网格 | cell_px | 玩法矩形 (x0,y0)-(x1,y1) |
|---|---|---|---|
| 1 | 11×7 | 114 | (333,113)-(1587,911) |
| 2 | 13×7 | 114 | (219,113)-(1701,911) |
| 3 | 16×10 | 80 | (320,112)-(1600,912) |
| 4 | 12×12 | 66 | (564,116)-(1356,908) |
| 5 | 16×9 | 88 | (256,116)-(1664,908) |
| 6 | 16×9 | 88 | (256,116)-(1664,908) |
| 7 | 13×9 | 88 | (388,116)-(1532,908) |
| 8 | 15×11 | 72 | (420,116)-(1500,908) |

新增工具 `tools/print_playfield_rects.py`：读取所有关卡 JSON 打印上表，并可输出 1920×1080 的"玩法区标线 PNG"供资源方垫底作图。`SimTypes.TILE_SIZE` 不再是固定常量，改为 `BattleRoot.cell_px`（每关计算）；模拟层不受影响。

### 1.3 数据

关卡 JSON 新增：
```json
"scene": {
  "backdrop": "res://assets/backdrops/level_01.png",
  "ground": "res://assets/grounds/bone_farm_a.png",
  "ground_tint": "#ffffff",
  "playfield_rect": null
}
```
- `backdrop`：1920×1080 整幅图。
- `ground`：可平铺的俯视地面贴图（每生态 2 张，512×512），只画在玩法矩形内，随网格平铺；alpha 0.9 叠在 backdrop 上，使玩法区与纯背景有可见但柔和的边界。
- `playfield_rect`：留空则按 1.2 计算；编辑器可手动微调（像素）。
- 旧字段 `background` 废弃；`biomes.json` 新增 `ground_marks`（障碍格地面标识贴片列表）与 `ground_textures`。

验收：竖立景物所在区域没有玩法格；玩法矩形外不可部署/移动/布点；三种窗口比例（16:9、16:10、21:9）下边界稳定。

## 3. 个人信标、路径模式、到点条件、定时等待（A06）【会议已定方向，细则为建议】

### 3.1 信标（Beacon）

- 每个己方单位拥有自己的信标序列，字母 A–H，最多 8 个。存于玩家配置（**第三阶段 10 §6.3 已改**：编号为数字 "1"、"2"…，无 8 个上限，旧字母兼容映射；存档 v4）：
  ```json
  "beacons": [ { "id": "A", "cell": [5, 6] }, { "id": "B", "cell": [9, 6] } ]
  ```
- 交互（仅部署阶段）：左键选中单位 → 在玩法区**右键**可行走格 = 追加下一个字母；右键已有信标 = 删除该信标（字母不重排，后续引用该字母的条件/行为标记失效并在校验中提示）；拖拽信标 = 移动。信标不能放在障碍格；可以放在任何可行走格（含部署区外）。
- 显示：选中单位的信标与连线高亮（骨白，alpha 0.85），其他单位的信标为小号浅印记（alpha 0.3）；运行中当前前往的信标闪烁。
- 关卡预设路线保留为只读参考（淡色虚线 + 名称），单位面板提供"复制预设路线为我的信标"按钮。敌人继续使用 `follow_route`。（**第三阶段 10 §7 已改**：预设路线显示删除，`routes` 数据保留给敌人；玩家菜单不再有"沿路线前进"（commands.json `player: false`）。）

### 3.2 行为 `follow_beacons`

```json
{ "type": "follow_beacons", "mode": "once" | "loop" | "pingpong", "from": "A" }
```
- `once`：A→B→…→末尾，到达后 `ROUTE_FINISHED` 原地等待（本条规则仍成立，不回退）。
- `loop`：末尾后回到 `from`。
- `pingpong`：末尾后反向，到 `from` 后再正向。
- 运行状态 `beacon_cursor {index, dir}` 存在单位上；被更高优先级规则抢占时保留，恢复后继续前往同一信标。信标序列在部署阶段修改后游标重置。
- 单位抵达判定：与信标格中心距离 < `ARRIVE_EPS`（0.05）。

### 3.3 条件 `at_beacon`

```json
{ "type": "at_beacon", "beacon": "A" }
```
持续成立型：单位中心与该信标格中心距离 ≤ 0.35 格即成立。信标不存在 → 条件视为不成立且校验报 `BEACON_MISSING`。

### 3.4 行为 `wait`

```json
{ "type": "wait", "seconds": 2.0 }
```
- 定时等待是**一次性（边沿触发）行为**，与"第一条成立即执行"的兼容规则如下：
  1. 每条含 `wait` 的规则维护 `armed` 标志，初始为 true。
  2. 规则条件成立且 `armed` → 规则被选中，开始计时（用模拟时间），单位原地不动不攻击；UI 显示剩余秒数。
  3. 计时结束 → `armed = false`，本步起该规则**视为不成立**，评估继续向下。
  4. 规则条件变为不成立（例如离开信标）→ `armed = true`。
  5. 被更高优先级规则抢占 → 计时取消且 `armed = false`（不重新计时），直到条件再次由假变真。
- 典型编排：`[射程内敌人→攻击] [到达A→等待2秒] [始终→沿信标 once]`。
- `wait` 不需要目标；`seconds` 范围 0.5–30。

### 3.5 优先级冲突细则【建议，对应纪要第 6 页"需要显式确定的交互"】
- 等待完成后如何推进：由下一条成立的规则决定（通常是 follow_beacons）。
- 到点条件为持续状态，一次性由 `wait` 的 armed 机制保证。
- 路径指令与攻击/撤离冲突：仍是列表顺序，无隐式优先。
- 运行中不允许改信标。

### 3.6 新增原因码与校验码
`ReasonCode`: `WAITING`, `BEACON_MISSING`。`validation`: `BEACON_MISSING`、`BEACON_ON_BLOCKED`、`BEACONS_EMPTY`（follow_beacons 但没有信标）。

### 3.7 验收小场景（纪要第 6 页整理建议）
一名单位、三枚信标：走到 A、等 2 秒、走到 B、再到 C 停下；再分别验证 loop 与 pingpong；删除 B 后引用 B 的条件在校验中被指出而非静默改指。写成 GUT 集成测试 `test_beacons_wait_scenario.gd`。

## 4. Cost 与自主出场选择（A07）【会议已定方向，价格为建议】

### 4.1 数据

`units.json` 每个己方形态新增 `"cost": 3`。
关卡 JSON `slots` 改为 `roster`：
```json
"roster": {
  "mode": "free",                    // "fixed" = 第一阶段固定槽位；"free" = 自主选择
  "budget": 10,
  "available_forms": ["striker", "bulwark", "swift"],   // null = 全部已解锁形态
  "max_units": 4,
  "min_units": 1,
  "fixed_slots": [ ...原 slots 结构去掉 rules，仅 mode=fixed 时使用... ]
}
```
- 预算与单价由数据定义；放置扣费、收回返还；HUD 底栏显示 `已用/预算`。
- 校验：`BUDGET_EXCEEDED`、`TOO_FEW_UNITS`（< min_units）、`FORM_NOT_AVAILABLE`。
- "空场白赢"由两处堵住：`min_units ≥ 1` 且护送/保护类关卡的被保护对象必须可被敌人威胁（关卡设计责任，编辑器试玩时检查）。

### 4.2 玩家配置与存档

`level_configs[level_id]` 由"槽位→配置"改为单位列表：
```json
"units": [ { "uid": "u1", "form": "bulwark", "pos": [3,4], "rules": [...], "beacons": [...] } ]
```
`uid` 在部署阶段分配（u1、u2…递增，不复用），己方模拟 id = `ALLY_ID_BASE + 序号`。旧存档的 `slot_*` 结构按 mode=fixed 关卡迁移，迁移失败标记 invalid 不删除。

### 4.3 解锁
`GameState.unlocks.forms` 决定全局可用形态；`available_forms` 再做关卡级限制。废弃 `unlocks.slots`。

## 6. 可读性与朝向（A03、A04）

- 路线/信标线：部署 alpha 0.85、运行 0.45，线宽 3px，骨白；预设路线为淡紫虚线。（第三阶段：预设路线显示删除，10 §7）

- 框架支持任意数量节点；本阶段章节 JSON 只放现有 8 关（编号不变）。解锁 = 存在一条已完成的前驱连线。选关界面画连线（已完成金色、可挑战骨白、锁定暗紫），节点显示状态与悬浮信息。
- 24 关的归属与新关内容暂缓，等编辑器完成后由策划编辑（08 决策 ①）。
