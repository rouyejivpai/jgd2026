## 0. 范围与顺序【用户已定】

录屏给出的整体方向有四条：统一美术与实现、改善操作流程、调整场景表现、先验证一个界面的制作流程再推广。据此第三阶段分两条并行线：

- **功能线（程序，不依赖美术）**：设置浮窗、章节地图改造、部署反馈、指令编辑重构、Cost 框架、局内 UI 重排、镜头横移、场景高亮、删预设路线。全部先用现有 `UiKit` 程序化样式做出来，布局位置按录屏意见摆放，等设计图到后只换皮不改功能。
- **美术线（GPT 绘图 → 切图 → 程序拼接）**：先由资源方统计全部需要绘制的 UI（R0），再只做**一个界面**（默认主界面 + 设置浮窗，决策 ③）走通"绘制 → 切图 → 拼接 → 与设计图比对"流程（R1 / P5），流程稳定后扩展到其余界面（R2–R5 / P6–P7）。

执行顺序：程序 P0 → P1 → P2 → P3 → P4 先行；P5 等 R1 交付；P6 等 R2/R3/R5；P7 等 R4。资源 R0 → R1 先行，R2–R5 在 R1 流程验证通过后开始。

**本阶段不做**：任何数值调整与指令 Cost 的具体数值（框架先行，数值后定【用户已定】）、关卡编辑器、新关内容、24 关归属、第七关数据、动画序列帧。

## 1. 美术管线「绘制 → 切图 → 拼接」【用户已定方向，格式为建议】

### 1.1 分工与验收标准
- GPT（资源方）出 **1920×1080 全幅设计图**，并按本节格式切图；Claude（程序方）只做拼接与接线。
- 验收标准：**最终界面与设计图一致，不是"相似"**。程序方交付每个界面的实机截图，用 `tools/ui_diff.py` 与设计图做像素比对（忽略文字反走样与动态内容区域，差异像素比例阈值 2%【建议】），比对图随 PROGRESS 提交；用户再目视确认。

### 1.2 交付格式（资源方 → 程序方）
每个界面一个目录 `godot/assets/ui/<screen>/`：
```
design.png                 1920×1080 完整设计图（含示例文字与状态）
slices/<element>.png       切片（透明 PNG；按钮等多状态按 _normal/_hover/_pressed/_disabled 后缀）
manifest.json              切片清单
```
`manifest.json`：
```json
{
  "schema_version": 1,
  "screen": "main_menu",
  "design_size": [1920, 1080],
  "elements": [
    { "id": "bg", "kind": "image", "file": "slices/bg.png", "rect": [0, 0, 1920, 1080] },
    { "id": "btn_start", "kind": "button", "rect": [760, 620, 400, 96],
      "states": { "normal": "slices/btn_start_normal.png", "hover": "...", "pressed": "...", "disabled": "..." },
      "ninepatch": [24, 24, 24, 24], "text_rect": [40, 20, 320, 56],
      "font": { "family": "NotoSerifSC", "size": 30, "color": "#e8dfcf" } },
    { "id": "panel_settings", "kind": "ninepatch", "file": "slices/panel.png", "rect": [560, 180, 800, 720], "ninepatch": [48, 64, 48, 48] },
    { "id": "icon_speed_1x", "kind": "icon", "file": "slices/icon_1x.png", "rect": [1700, 24, 48, 48] }
  ]
}
```
`kind` ∈ `image | ninepatch | button | icon | toggle | slider | text_style`。`rect` 为设计图坐标，程序方据此生成布局。可复用的公共件（面板、按钮、滑条、下拉）放 `assets/ui/common/`。

#### 1.2 增补（P5 实测，2026-10-05，见 QUESTIONS Q-069 ~ Q-071）
- 所有显示文字都要在 TEXT_BINDINGS 给出 strings key（动态值注明格式来源）；主界面副标题已补 `ui.game_subtitle`。
- 下拉：`dropdown_<名>`（button）与显示值 `<名>_value`（text_style）配对，值的字体与位置并入下拉；箭头为独立 icon。
- 滑条：轨 / 填充（ninepatch）+ 把手（icon）三层；运行时满宽 = 轨右端 − 填充左端，填充宽 = floor(满宽 × 值)，把手 x = floor(填充末端 − 把手宽 / 2)；把手各状态按 `slider_grabber_<状态>.png` 放在同目录。
- 焦点复用 hover 贴图；错误态 manifest 只贡献主 manifest 没有的元素与按钮禁用字色。
- 设计图按 sRGB 空间合成；程序在菜单类界面关闭 HDR 2D 以保持一致（战斗场景仍为 HDR，局内 UI 换皮需另定，Q-069）。
- 比对：`tools/ui_diff.py` 只在文字区允许 ±1 px 位移匹配（字形栅格化差异），面板、控件、贴图不豁免；动态内容用 `--ignore` 显式列出。

### 1.3 程序接入机制
- `tools/apply_ui_manifest.py <screen>`：读 manifest，生成 `assets/themes/ui_<screen>.tres`（StyleBoxTexture / 图标 / 字号）与 `data/ui_layout/<screen>.json`（每个元素的 rect，设计坐标），并更新 `.import` 预设（UI 贴图 Lossless、无 mipmap、线性过滤）。
- UI 脚本只读 `data/ui_layout/<screen>.json` 与 theme，**不写布局数字**（铁律 4 的延伸：布局进 JSON）。窗口比例变化按 07 §1 的居中规则缩放，设计坐标 → 屏幕坐标只在 `UiKit.layout_rect()` 一处换算。
- 换皮不得改功能代码路径；换皮前后 GUT 全绿、`run_playtests` 哈希不变。

### 1.4 试做界面
默认 **主界面 + 设置浮窗**（决策 ③）：元素最少、设置浮窗在三个界面复用，能同时验证静态页与浮窗两种结构。流程不通则先改 §1.2 格式，再继续其他界面。

### 1.5 UI 动效：按钮动效与艺术字动效【用户已定：先主界面试做，通过后通用；追加于 2026-10-05】
- **范围**：(a) 按钮动效：hover / pressed / disabled 的状态过渡与反馈，可含微弱待机；(b) 艺术字动效：标题类美术字的入场或持续动效，范围清单见决策 ⑭（主界面标题先做）。普通正文、按钮文字、数字不做。
- **分工**：按钮动效由**程序方会话自主设计**并实现（Tween 或 CanvasItem 着色器，基于现有切片，不自行画素材；需要额外图层如高光扫过遮罩时经 QUESTIONS 向资源方索取）。艺术字动效的视觉由**资源方会话自主设计**，交付可动的分层素材或帧序列并附动效说明，程序方按说明实现播放。
- **顺序**：先只做主界面（开始 / 设置 / 退出三个按钮 + 标题艺术字）→ 用户目视判断 → 通过后：按钮动效经 `UiKit` 统一挂到全部按钮（换皮界面与程序化占位界面都生效，不逐界面写）；艺术字按决策 ⑭ 清单逐个接入。
- **交付格式（资源方）**：`assets/ui/<screen>/art_text/<id>/`，分层素材（`base.png` 底字、`glow.png` 发光 / 自发光遮罩、`ember.png` 火星 / 粒子遮罩等，按设计需要）或帧序列（`frames/0001.png…` + fps；`tools/gen_burning_text.py` 可作帧序列生成起点），加 `motion.md`（时长、循环方式、节奏、图层叠加与混合模式）。manifest 新增 `kind: "art_text"`，`rect` 为静止态位置，`layers[]` 或 `frames` 字段指向文件。
- **约束**：
  1. 动效不改布局：静止态（无悬停、无按下、t = 0 或帧 0）必须与设计图一致；`ui_diff.py` 比对时用 `UiKit.motion_enabled = false`（截图工具参数 `--no-motion`）冻结在静止态。
  2. 状态过渡时长 ≤ 0.25 s【建议】；待机循环幅度小、不抢焦点；任意时刻可被下一状态打断且不残留；disabled 不播放。
  3. 只在表现层（Control / CanvasItem 着色器 / Tween），不碰模拟与存档；GUT 全绿、`run_playtests -- --check` 全等。
  4. 性能：主界面全部动效开启时 1080p 稳定 60 fps；着色器只用 `TIME` 与自身 uniform，不读全局状态。
  5. 本阶段不新增「关闭动效」设置项，`motion_enabled` 只作代码级总闸保留。
- **数据**：动效参数（时长、曲线名、循环、幅度）写在 manifest 元素的 `motion` 字段或 `data/ui_motion.json`（程序方自定其一），必须是数据而非代码常量（铁律 4）。

- **数组顺序 = 菜单顺序 = 默认项**（第一项为默认）【用户已定】。条件默认「始终」。
- `unlock_key` 复用现有 `preset.*` 键，`progression.json` 与关卡 `rewards` **不改**；关卡 `allowed` 继续按 action / condition / selector 过滤。解锁语义：键为空 = 始终可用（沿用 Q-047）。
- `player: false` 的行为不进玩家菜单（预设路线只给敌人数据用，与 §7 删路线显示一致）。
- `presets.json`：`DataRegistry` 不再加载；文件在 P1 末删除，`02` 文档同步；`validate_data.py` 改为校验 `commands.json`（id 必须是 `SimTypes` 可解析值、unlock_key 必须在 progression 或任一关卡 rewards 中出现）。
- 标签与整句模板沿用 `strings.json` 的 `action_text / condition_text / selector_text / filter_text`。

### 5.2 RuleDef 契约不变
- `conditions[]`、`condition_mode (all|any)`、`enabled` 字段全部保留。UI 限制条件 **≤ 2**；敌人数据可多于 2，只读面板全部显示。
- `enabled` 不再显示（勾选框删除【用户已定】）；UI 写出恒为 `true`；读到旧存档 `enabled: false` 的玩家配置时视为 `true` 并在下次保存写回（记 CHANGELOG）。评估器不改。
- `condition_mode` 由「与 / 或」切换按钮控制，仅两条件时显示；一条或零条件时写 `all`。

### 5.3 RuleRow 结构（行为在上、条件在下）
```
[≡] [行为 ▾] [行为参数：目标选择 ▾ / 目标类型 ▾ / 信标模式 ▾ 起点 ▾ / 等待秒数]            [删除]
    条件一 [▾] [参数]
    [与|或] 条件二 [▾] [参数]          ← 条件二默认「无」，选了才存在
    整句预览 ／ 运行中：为何不成立
```
- 行为参数按行为需要显示：`attack / chase_attack / chase` 显示目标选择与目标类型；`follow_beacons` 显示模式与起点；`wait` 显示秒数；`retreat / idle` 无参数。`target_distance` 条件需要目标时复用行为的目标选择，行为无目标时在条件行内显示目标选择。
- 删除按钮、拖拽排序、运行中金边与"为何不成立"保持。
- 敌人只读面板同布局。

### 5.4 添加流程
「添加指令」→ 弹出**行为列表**（`commands.actions` 中 `player` ∧ 已解锁 ∧ 本关 allowed）→ 选中即在末尾新增一行：条件「始终」，目标选择 / 目标类型 / 模式 / 起点等取各自列表首个可用项，等待秒数取 `WAIT_MIN_SECONDS`。不再出现预组合指令。

### 5.5 Cost 框架（数值后定【用户已定】）
- 指令 Cost = Σ 每条指令 (`action.cost` + Σ `condition.cost`)；单位总 Cost = 形态 `cost` + 指令 Cost；关卡预算校验 `BUDGET_EXCEEDED` 按总 Cost 计；`controller.budget_used()` 含指令。
- HUD 预算显示 `已用 / 预算`；侧栏显示本单位「形态 N ＋ 指令 M」。编辑指令时实时刷新；超预算时允许继续编辑但校验阻塞开始（与现有预算校验一致）。
- 本阶段 `commands.json` 全部 `cost = 0`，因此 8 关与推荐阵型、试玩场景结果不变（验收要求 `run_playtests` 哈希全等）。

## 6. 局内 UI 重排（意见书 05、07）【用户已定方向，位置待设计图】
